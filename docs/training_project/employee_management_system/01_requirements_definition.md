# 员工管理系统要件定义

> 文档状态：教学基线  
> 适用范围：前端、Python Web、Java/Spring Boot、数据库、测试与部署课程

## 一、项目背景

某公司目前通过多个 Excel 文件管理员工与部门信息，存在以下问题：

- 文件分散，难以确认最新版本
- 多人修改时容易覆盖
- 员工状态和部门名称不统一
- 查询和统计效率低
- 重要修改没有操作记录
- CSV 导入错误难以定位

公司决定开发一个前后端分离的员工管理系统，集中管理员工、部门、账号和操作记录。

## 二、项目目标

- 统一管理员工和部门数据
- 通过角色限制查看和修改权限
- 提供稳定的查询、新增、修改和逻辑删除功能
- 支持 CSV 批量导入和 Excel 报表导出
- 对重要操作保留日志
- 建立可以测试、部署和维护的标准 Web 项目

## 三、参与者

| 参与者 | 主要工作 |
| --- | --- |
| 系统管理员 | 管理账号、角色、员工、部门和操作日志 |
| 人事担当 | 登记、修改、导入和导出员工信息 |
| 只读用户 | 查询员工与部门信息 |
| 系统运维人员 | 配置、部署、监控、备份和故障调查 |

## 四、功能要件

### 4.1 认证与会话

| 要件 ID | 要件 |
| --- | --- |
| `FR-AUTH-001` | 用户可以使用登录 ID 和密码登录 |
| `FR-AUTH-002` | 登录失败时返回统一错误，不泄露账号是否存在 |
| `FR-AUTH-003` | 登录成功后，后续请求能够识别当前用户 |
| `FR-AUTH-004` | 用户可以退出登录，使当前会话或 Token 失效 |
| `FR-AUTH-005` | 无效或过期凭据不能访问受保护接口 |

### 4.2 员工查询

| 要件 ID | 要件 |
| --- | --- |
| `FR-EMP-001` | 用户可以分页查询员工列表 |
| `FR-EMP-002` | 可以按员工姓名进行部分匹配查询 |
| `FR-EMP-003` | 可以按部门和员工状态筛选 |
| `FR-EMP-004` | 可以按员工编号查询员工详情 |
| `FR-EMP-005` | 列表可以按员工编号、入职日期或更新时间排序 |

### 4.3 员工维护

| 要件 ID | 要件 |
| --- | --- |
| `FR-EMP-101` | 人事担当和系统管理员可以新增员工 |
| `FR-EMP-102` | 员工编号必须唯一 |
| `FR-EMP-103` | 邮箱必须唯一 |
| `FR-EMP-104` | 员工必须属于一个有效部门 |
| `FR-EMP-105` | 人事担当和系统管理员可以修改员工信息 |
| `FR-EMP-106` | 系统管理员可以逻辑删除员工 |
| `FR-EMP-107` | 已逻辑删除员工默认不出现在普通列表中 |
| `FR-EMP-108` | 同时修改同一员工时，系统应能发现版本冲突 |

### 4.4 部门管理

| 要件 ID | 要件 |
| --- | --- |
| `FR-DEPT-001` | 用户可以查询有效部门列表 |
| `FR-DEPT-002` | 系统管理员和人事担当可以新增部门 |
| `FR-DEPT-003` | 部门编号和部门名称必须唯一 |
| `FR-DEPT-004` | 系统管理员和人事担当可以修改部门名称 |
| `FR-DEPT-005` | 存在有效员工的部门不能直接停用 |

### 4.5 CSV 导入与 Excel 导出

| 要件 ID | 要件 |
| --- | --- |
| `FR-FILE-001` | 人事担当和系统管理员可以上传 UTF-8 CSV 员工文件 |
| `FR-FILE-002` | CSV 必须检查表头、必填、格式、重复和关联部门 |
| `FR-FILE-003` | 导入失败时应返回行号、字段和错误原因 |
| `FR-FILE-004` | 基础版本采用全件校验后统一登记，存在错误时不登记任何行 |
| `FR-FILE-005` | 单次导入上限为 1000 行，文件上限为 5 MB |
| `FR-FILE-006` | 用户可以按照当前查询条件导出员工 Excel 报表 |

### 4.6 操作日志

| 要件 ID | 要件 |
| --- | --- |
| `FR-AUDIT-001` | 登录、员工新增、修改、删除和 CSV 导入必须记录操作日志 |
| `FR-AUDIT-002` | 日志记录操作者、操作类型、对象、时间和结果 |
| `FR-AUDIT-003` | 操作日志不得记录密码、完整 Token 或其他秘密 |
| `FR-AUDIT-004` | 只有系统管理员可以查询操作日志 |

## 六、核心业务规则

### 6.1 员工编号

- 格式：`EMP` 加 4 位数字，例如 `EMP0001`
- 创建后不可修改
- 大小写统一为大写
- 逻辑删除后也不能立即复用

### 6.2 部门编号

- 格式：`D` 加 3 位数字，例如 `D001`
- 创建后不可修改
- 被员工引用时不能删除

### 6.3 员工状态

| 状态 | 含义 |
| --- | --- |
| `ACTIVE` | 在职 |
| `LEAVE` | 休职 |
| `RETIRED` | 退职或逻辑删除 |

允许的基础状态变化：

```text
ACTIVE → LEAVE
LEAVE → ACTIVE
ACTIVE → RETIRED
LEAVE → RETIRED
```

基础版本不允许将 `RETIRED` 直接恢复为 `ACTIVE`，恢复需求作为后续扩展。

### 6.4 邮箱

- 必填
- 必须符合邮箱基本格式
- 不区分大小写判断重复
- 存储前去除首尾空格

### 6.5 日期

- 入职日期使用 `YYYY-MM-DD`
- 接口日期时间使用 ISO 8601
- 日期时间包含时区或统一按项目约定处理
- 不使用本地化显示文字作为接口数据

### 6.6 并发修改

员工数据包含 `version`。更新时客户端提交当前版本，服务端发现版本不一致时返回冲突，避免后提交者无提示覆盖他人修改。

## 七、非功能要件

### 7.1 安全

- 密码不得明文保存
- 正式通信使用 HTTPS
- 后端执行认证和授权
- 不在 URL、日志和前端代码中保存秘密
- 上传文件检查大小、扩展名、内容格式和行数
- 数据库操作使用参数绑定或 ORM，避免 SQL 注入

### 7.2 可维护性

- 前端、后端和数据库职责清楚
- 接口字段和错误结构统一
- 环境配置不硬编码
- 重要处理保留日志
- 核心业务具有自动化测试
- README 可以帮助新成员重建环境

### 7.3 可用性

- 页面必须展示加载中、无数据、成功和失败状态
- 表单错误应定位到具体字段
- 重复提交应被阻止或由后端安全处理
- 导入和导出应给出可确认的结果

### 7.4 性能教学目标

- 员工列表必须分页，默认每页 20 条，最大 100 条
- 避免在列表中逐行追加查询造成 N+1 问题
- 导入不得把无限制文件一次性读入内存
- 性能结论必须通过日志、计时或执行计划确认

这些是教学验收目标，不代表真实生产 SLA。生产指标需要根据业务量和环境重新定义。

### 7.5 可观测性

- 请求和错误应具有可追踪编号
- 日志包含时间、级别、处理位置和必要业务标识
- 健康检查不返回秘密
- 服务器异常不把堆栈直接返回给客户端

## 八、验收场景

### 8.1 正常场景

1. 人事担当登录。
2. 创建部门 `D001`。
3. 创建员工 `EMP0001`。
4. 在员工列表中按姓名查询。
5. 修改员工邮箱。
6. 导出当前查询结果。
7. 查看操作结果和日志。

### 8.2 异常场景

- 未登录访问员工接口返回 `401`
- 只读用户新增员工返回 `403`
- 查询不存在员工返回 `404`
- 重复员工编号或邮箱返回 `409`
- 字段格式错误返回项目规定的校验错误
- 使用旧版本更新员工返回 `409`
- CSV 存在错误时整批不登记，并返回错误明细

### 8.3 边界场景

- 姓名达到最大长度
- 列表为空
- 最后一页不足 20 条
- CSV 正好 1000 行
- 文件正好达到大小上限
- 同一时间两人编辑同一员工

## 九、项目完成条件

- 必须功能可以从前端正常操作
- API 与接口规格一致
- 数据库约束和业务规则一致
- 权限在前后端均正确处理
- 正常、异常和边界测试通过
- 不提交真实秘密和本地虚拟环境
- README 包含搭建、运行、测试和停止步骤
- 提供主要画面和接口测试证据
