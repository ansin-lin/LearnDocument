# Web 开发基础概念

> 本章用于帮助新人建立 Web 系统开发的整体认识。内容不依赖某一种编程语言，可作为 Python Web、Java Web、Vue、React 等课程的共同前置知识。

## 一、学习目标

完成本章后，学员应能够：

- 用自己的语言说明什么是 Web 系统
- 说明浏览器、前端、后端和数据库之间的关系
- 区分前端与后端的主要职责和常用技术
- 说清一次请求从页面发出到结果显示的基本过程
- 理解 MVC、三层架构和前后端分离的基本思想
- 区分单体应用与微服务，并了解各自适用的场景
- 了解一个 Web 项目从需求到上线维护的基本流程
- 看懂日本项目中常见的开发阶段和工作术语

## 二、什么是 Web 开发

Web 开发是围绕浏览器、服务器和网络通信构建应用系统的开发方式。用户通常通过浏览器访问系统，系统接收用户操作，处理业务并返回结果。

常见的 Web 系统包括：

- 企业内部管理系统
- 用户、商品和订单管理系统
- 银行、保险和电商系统
- 信息查询和报表系统
- 对外提供数据的 API 服务

一个完整的 Web 系统通常不只有页面，还可能包含前端程序、后端服务、数据库、文件存储、登录认证、日志、测试和部署环境。

## 三、Web 系统的主要组成

```text
用户
  ↓ 操作页面
浏览器中的前端程序
  ↓ HTTP 请求
Web 服务器 / 后端程序
  ↓ 执行业务逻辑
数据库、文件或外部系统
  ↑ 返回数据
后端程序
  ↑ HTTP 响应
前端程序更新页面
```

### 3.1 浏览器

浏览器是用户访问 Web 系统的入口，例如 Chrome、Edge 和 Safari。它负责：

- 解析 HTML 并显示页面结构
- 使用 CSS 设置页面样式
- 执行 JavaScript，实现页面交互
- 向后端发送 HTTP 请求
- 接收后端返回的 HTML、JSON、图片或文件

### 3.2 Web 服务器

Web 服务器用于接收网络请求并返回响应。实际项目中，“Web 服务器”有时指 Nginx、Apache 等服务器软件，有时也泛指运行后端程序的服务端环境。

例如，Nginx 可以负责接收请求、提供静态文件、转发请求和负载均衡，再把业务请求交给 Python 或 Java 后端程序处理。

### 3.3 数据库和外部系统

数据库用于长期保存用户、商品、订单等业务数据。后端还可能调用其他公司的 API、邮件服务、文件服务器和云服务。

常见数据库包括 MySQL、PostgreSQL、Oracle 和 SQL Server。

## 四、前端是做什么的

前端是用户能够直接看到和操作的部分，主要运行在浏览器中。

### 4.1 前端的主要职责

- 展示文字、图片、表格、表单和按钮
- 接收点击、输入、选择和拖拽等用户操作
- 对输入内容进行基础校验
- 调用后端接口并处理返回结果
- 根据数据更新页面
- 处理页面跳转、菜单和登录状态

前端校验可以改善用户体验，但不能代替后端校验。例如，前端可以提示“用户名不能为空”，后端仍然必须再次检查，因为请求可能绕过页面直接发送。

### 4.2 前端常用技术

| 类别 | 常用技术 | 主要作用 |
| --- | --- | --- |
| 页面结构 | HTML | 定义标题、表单、表格等页面内容 |
| 页面样式 | CSS | 设置颜色、布局、字体和响应式效果 |
| 页面逻辑 | JavaScript、ES6+ | 处理交互、数据和浏览器操作 |
| 类型与工程化 | TypeScript | 为 JavaScript 增加类型检查，提高可维护性 |
| 前端框架 | Vue、React | 以组件方式构建复杂页面 |
| 网络请求 | Fetch、Axios | 调用后端 API |
| 构建工具 | Vite、npm | 管理依赖、启动开发环境和构建项目 |

## 五、后端是做什么的

后端通常运行在服务器上，用户不能直接看到后端代码。它负责接收请求、执行核心业务规则、访问数据并返回结果。

### 5.1 后端的主要职责

- 接收并解析前端请求
- 校验请求参数和数据合法性
- 执行登录、下单、审批等业务逻辑
- 查询、保存和修改数据库数据
- 进行身份认证和权限判断
- 调用外部 API、发送邮件或执行批处理
- 记录运行日志并处理异常
- 返回 JSON、HTML、文件或错误信息

### 5.2 后端常用技术

| 类别 | Python Web | Java Web | 主要作用 |
| --- | --- | --- | --- |
| 编程语言 | Python | Java | 编写业务逻辑 |
| Web 框架 | Django、Flask、FastAPI | Spring Boot、Spring MVC | 接收请求、配置路由并返回响应 |
| 数据访问 | SQLAlchemy、Django ORM | MyBatis、JPA | 操作数据库 |
| 参数校验 | Pydantic、Django Form | Bean Validation | 检查输入数据 |
| 测试 | pytest | JUnit | 验证程序行为 |
| 构建与依赖 | pip、venv、Poetry | Maven、Gradle | 管理依赖和项目环境 |
| 部署运行 | Uvicorn、Gunicorn | 内嵌 Tomcat 等 | 运行后端应用 |

框架和工具会不同，但 Python Web 与 Java Web 处理的问题基本相同：请求、业务、数据、权限、日志、测试和部署。

## 六、一次 Web 请求发生了什么

以“用户登录”为例：

1. 用户在登录页面输入账号和密码。
2. 前端检查必填项，并向后端登录地址发送 HTTP 请求。
3. Web 服务器接收请求并转交给后端程序。
4. 后端根据请求地址找到对应的处理程序。
5. 后端校验参数，并从数据库查询用户信息。
6. 后端判断密码是否正确、账号是否可用。
7. 登录成功时，后端创建 Session 或 Token。
8. 后端通过 HTTP 响应返回处理结果。
9. 前端读取结果，跳转到首页或显示错误信息。

```text
登录页面
  ↓ POST /api/login
Controller / 路由处理
  ↓ 调用
Service / 业务处理
  ↓ 查询
Repository、Mapper / 数据访问
  ↓ SQL
数据库
  ↑ 查询结果
后端返回登录结果
  ↑ JSON 响应
前端显示结果
```

这一过程体现了 Web 开发的核心：客户端发送请求，服务器处理请求并返回响应。

## 七、前后端分离

### 7.1 什么是前后端分离

前后端分离是指前端和后端分别开发，通过 HTTP 接口交换数据。后端通常返回 JSON，前端根据 JSON 更新页面。

```text
Vue / React 前端  ← HTTP + JSON →  Python / Java 后端
```

### 7.2 为什么使用前后端分离

- 前端与后端职责更清楚
- 双方可以根据接口定义并行开发
- 同一套后端接口可以服务网页、App 等多个客户端
- 页面和后端可以分别测试、构建和部署

### 7.3 前后端如何协作

开发前通常需要确认接口定义，包括：

- 请求地址和 HTTP 方法
- 请求参数的名称、类型和是否必填
- 响应数据的字段和类型
- 成功与失败时的状态码
- 登录认证方式
- 错误信息格式

如果接口定义不明确，容易出现字段名不同、数据类型不同或错误处理不一致等联调问题。

## 八、常见开发模式

开发模式用于划分职责，让代码更容易理解、修改和测试。MVC 和分层架构解决的是代码如何组织的问题，前后端分离解决的是前端与后端如何协作的问题，它们可以同时使用。

### 8.1 MVC 模式

MVC 将程序划分为三个角色：

| 组成 | 含义 | 主要职责 |
| --- | --- | --- |
| Model | 模型 | 表示数据和处理与数据相关的规则 |
| View | 视图 | 向用户展示结果 |
| Controller | 控制器 | 接收请求、调用处理逻辑并决定返回内容 |

在传统服务端页面项目中，View 可能是服务器生成的 HTML。在前后端分离项目中，后端的 Controller 通常返回 JSON，真正的页面展示由 Vue 或 React 完成。

### 8.2 Django 的 MTV

Django 常使用 MTV 这个名称：

- Model：数据模型
- Template：页面模板
- View：接收请求并协调处理

MTV 与 MVC 的命名不同，但核心思想相近，都是分离不同职责。

### 8.3 分层架构

企业后端项目常见的分层方式如下：

| 层 | 常见名称 | 主要职责 | 不应该承担的职责 |
| --- | --- | --- | --- |
| 接口层 | Controller、Router、View | 接收请求、基础校验、返回响应 | 编写大量业务规则 |
| 业务层 | Service | 执行业务规则、组织处理流程、管理事务 | 直接拼接页面 |
| 数据访问层 | Repository、DAO、Mapper | 查询和修改数据库 | 决定业务流程 |
| 数据模型层 | Entity、Model、DTO | 表示数据库数据或接口数据 | 执行完整业务流程 |
| 公共基础层 | Config、Utils、Common | 配置、日志和通用功能 | 放置所有无法分类的代码 |

Python 与 Java 的类名、目录名可能不同，但分层目的相同：让每一层只负责一类工作。

### 8.4 为什么需要分层

- 修改页面接口时，尽量不影响数据库代码
- 修改数据库实现时，尽量不影响业务规则
- 可以分别测试接口、业务和数据访问逻辑
- 多人开发时更容易划分任务
- Code Review 时更容易判断修改范围

分层不是层数越多越好。小型系统可以使用简单结构，大型系统再根据复杂度增加层次。

## 九、单体应用与微服务

### 9.1 单体应用

单体应用通常把多个业务功能放在一个项目中，并作为一个整体构建和部署。

```text
一个应用
├── 用户管理
├── 商品管理
├── 订单管理
└── 报表管理
```

优点：

- 项目结构和部署方式相对简单
- 本地开发、调试和测试更直接
- 适合新人学习和中小型项目

需要注意的问题：

- 系统变大后，模块之间可能相互影响
- 一次发布通常需要部署整个应用
- 代码边界不清时容易形成复杂依赖

### 9.2 微服务

微服务把大型系统按业务边界拆成多个可以独立开发和部署的服务。

```text
前端 / API 网关
├── 用户服务
├── 商品服务
├── 订单服务
└── 支付服务
```

优点：

- 不同服务可以独立开发和发布
- 可以根据业务压力分别扩容
- 大型团队可以按服务划分职责

需要注意的问题：

- 服务之间需要通过网络通信
- 日志追踪、事务、部署和监控更加复杂
- 系统故障调查和测试成本更高

### 9.3 新人应该如何理解

单体与微服务不是“旧技术”和“新技术”的区别，也不是微服务一定更好。架构选择取决于业务规模、团队人数、发布方式和运维能力。

新人应先掌握单体项目中的请求处理、分层、数据库、测试和部署，再了解微服务之间的调用与治理。

## 十、Web 项目的基本开发流程

一个 Web 功能通常会经历以下过程：

1. **需求确认**：确认为什么开发、由谁使用、需要完成什么功能。
2. **需求分析**：整理业务规则、正常流程、异常流程和权限要求。
3. **设计**：设计页面、接口、数据库、处理流程和错误处理方式。
4. **任务分解**：把功能拆分为前端、后端、数据库和测试任务。
5. **开发环境准备**：取得代码，安装依赖，准备配置和数据库。
6. **编码实现**：按照设计完成页面、接口、业务逻辑和数据访问。
7. **开发者自测**：确认正常情况、异常情况和边界情况。
8. **Code Review**：由其他成员检查实现、规范、影响范围和测试结果。
9. **测试**：进行单体测试、结合测试、系统测试和必要的回归测试。
10. **发布上线**：将经过确认的版本部署到目标环境。
11. **运行维护**：监控日志，处理故障、咨询和后续改修。

开发不是“写完代码就结束”。设计、测试、Review、发布和维护都是项目开发的一部分。

## 十一、日本项目中的常见开发流程

不同公司和项目会有差异，但日本项目中经常看到以下阶段：

| 阶段 | 日语 | 主要工作 |
| --- | --- | --- |
| 需求定义 | 要件定義（ようけんていぎ） | 明确业务目标、范围和系统需求 |
| 基本设计 | 基本設計（きほんせっけい） | 设计画面、接口、数据库和系统整体行为 |
| 详细设计 | 詳細設計（しょうさいせっけい） | 细化处理流程、类、方法和数据项目 |
| 编码实现 | 製造・実装（せいぞう・じっそう） | 根据设计书编写代码 |
| 单体测试 | 単体試験（たんたいしけん） | 验证方法、类、模块或单个功能 |
| 结合测试 | 結合試験（けつごうしけん） | 验证前后端、模块和外部系统的连接 |
| 系统测试 | 総合試験（そうごうしけん） | 从整体业务和系统角度进行验证 |
| 用户验收 | 受入試験（うけいれしけん） | 由客户或业务方确认是否满足需求 |
| 发布 | リリース | 将系统或功能部署到正式环境 |
| 维护 | 保守・運用（ほしゅ・うんよう） | 监控运行、处理故障和追加改修 |

### 11.1 新人在日本项目中的常见工作

新人可能从以下工作开始：

- 阅读设计书和现有代码
- 根据详细设计进行实现
- 编写并执行单体测试
- 保存测试证据，例如画面截图和数据库结果
- 提交代码并接受 Review
- 根据指摘内容修改代码和文档
- 调查日志、复现问题并说明原因

### 11.2 日本项目中需要重视的事项

- 开发前确认需求和设计，不凭个人理解直接扩大修改范围
- 代码、设计书、测试项目和实际结果保持一致
- 修改时说明目的、影响范围和验证结果
- 保留清楚的日志、操作步骤和测试证据
- 收到 Review 指摘后确认原因，再进行对应
- 遇到不明确内容时及时报告、联络和商量

常见的“報告・連絡・相談（ほうこく・れんらく・そうだん）”简称“報連相（ほうれんそう）”，强调项目中的信息共享。它不是频繁发送无内容的消息，而是在适当时间让相关人员了解进度、风险和需要确认的问题。

## 十二、容易混淆的概念

### 12.1 前端校验与后端校验

前端校验主要改善操作体验，后端校验负责保护系统和业务数据，两者都需要。

### 12.2 MVC 与三层架构

MVC 主要说明 Model、View、Controller 的职责；三层架构通常关注接口、业务和数据访问的分层。它们观察问题的角度不同，可以同时存在于一个项目中。

### 12.3 前后端分离与微服务

前后端分离是客户端与服务端的协作方式；微服务是后端系统的拆分方式。前后端分离项目既可以使用单体后端，也可以使用微服务后端。

### 12.4 框架与架构

Spring Boot、Django 和 FastAPI 是帮助开发应用的框架；MVC、分层架构、单体和微服务是组织系统的思想或形式。使用某个框架不代表系统只能采用一种架构。

## 十三、基础练习

以“员工请假申请系统”为例，完成以下内容：

1. 列出前端需要完成的三项工作。
2. 列出后端需要完成的三项工作。
3. 说明数据库需要保存哪些主要数据。
4. 按照请求与响应的顺序，说明员工提交请假申请后发生了什么。
5. 判断该系统在公司内部小范围使用时，先采用单体还是微服务更合适，并说明理由。

## 十四、本章总结

- Web 系统通常由前端、后端、数据库及运行环境共同组成。
- 前端负责页面展示和用户交互，后端负责业务、数据、权限和系统处理。
- HTTP 请求与响应连接了浏览器和后端服务。
- MVC、MTV 和分层架构用于分离职责，提高可维护性。
- 单体和微服务各有适用场景，新人应先理解单体项目的完整开发过程。
- Web 开发包含需求、设计、实现、Review、测试、发布和维护，不只是编写代码。
- 日本项目重视设计与实现一致、修改范围明确、测试证据和团队信息共享。
