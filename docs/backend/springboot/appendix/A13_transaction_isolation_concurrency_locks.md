# A13 事务、并发更新与数据库锁——讲师导航

本页供讲师安排附录学习与核对实验结果；学员从[第13章主线](../mainline/13_transaction_and_consistency.md)进入相应附录即可。

## 学员应该按什么顺序学习？

本系列围绕一个真实业务事故：**A、B两名管理员打开同一员工页面，A保存姓名，B后来用旧表单保存邮箱，导致A修改被覆盖。** 不先让学员背锁的分类，而是先看见问题、做实验，再理解底层实现。

| 建议课次 | 学习文件 | 核心问题 | 实践结果 |
| --- | --- | --- | --- |
| 第1课 | [A13-1 事务与Spring机制](A13_01_transaction_spring_mechanisms.md) | `@Transactional`保障什么，为什么挡不住旧页面覆盖？ | 员工UPDATE＋履历INSERT共同提交/回滚 |
| 第2～3课 | [A13-2 并发更新与锁](A13_02_concurrent_updates_locks.md) | `FOR UPDATE`如何等待？为什么仍不能判断页面过期？`version`如何拒绝覆盖？ | 双MySQL连接观察等待；1行/0行与409；履历不误写 |
| 第4课 | [A13-3 隔离级别与MVCC](A13_03_isolation_mvcc.md) | 普通SELECT为什么能读？RC/RR为何不一样？索引为何改变锁范围？ | 对照快照读/当前读、不同隔离级别 |

附录按 `A13-1 → A13-2 → A13-3` 学习；第13章主线仍以员工更新和履历写入的共同提交、回滚为目标。锁和MVCC实验是独立扩展，不要求一次全部并入主线工程。

## 课堂统一案例与验收要求

**初始状态：** employee 1001为`Tanaka / Sales / old@example.com`。两人读取相同版本；A修改姓名，B只想修改邮箱。教学实验统一要求记录：请求顺序、完整请求体、事务边界、SQL、影响行数、HTTP状态、数据库最终姓名/邮箱/version、履历条数与记录。

1. **无并发控制：** 演示B用旧完整表单覆盖A，两个请求可能都成功。
2. **事务：** 员工更新与履历写入同一事务；履历失败则共同回滚，但旧表单仍可能覆盖。
3. **悲观锁：** 两个连接验证A `FOR UPDATE`、B等待、A提交、B继续；要求讲清谁加锁、锁定范围与何时释放。
4. **旧页面反例：** B十分钟后拿到锁仍提交旧字段；证明锁不自动检查请求数据的新旧。
5. **乐观锁：** 详情返回旧version、更新按`id+version`条件更新；A影响1行，B影响0行/HTTP409，不覆盖、不写成功履历，不自动重试旧表单。
6. **最后讲机制：** 约束、条件UPDATE、S/X、Record/Gap/Next-Key、RC/RR、MVCC、索引、等待和死锁。

## 环境边界与授课约束

- 课程示例默认Spring Boot 4.1.1、Java 17、MyBatis与MySQL 8.0 InnoDB；要使用与主线工程兼容的实际依赖和类名。
- `version`、休假余额、额外Mapper等是**独立实验扩展**，在专用可重建的个人练习库/分支实施；没有完成DTO、SQL、异常和测试全链路时不宣称示例可运行。
- 实验不得在生产、共享开发或其他学员共用库上执行；动手之前记录原数据/建表结构/履历，结束后按明确恢复计划核对，绝不随意清空履历或删表。
- JUnit + Mockito用于验证Service处理影响行数和异常的逻辑；**真实锁等待及SQL并发安全**必须通过真实InnoDB的两个连接或集成测试验证。

## 讲师快速问答

| 提问 | 要点 |
| --- | --- |
| 有`@Transactional`就没有并发覆盖了吗？ | 不会自动检查客户端页面数据是否过期 |
| `FOR UPDATE`是不是阻止所有SELECT？ | 普通MVCC一致性读通常仍可读快照 |
| 乐观锁是不是数据库完全不加锁？ | 条件UPDATE仍使用必要的数据库写锁 |
| 影响行数0一定是version冲突吗？ | 也可能不存在，需要按契约区分404/409 |
| 有索引为什么还可能等待？ | 相同记录写入冲突依旧存在；索引主要影响检索和锁定范围 |
