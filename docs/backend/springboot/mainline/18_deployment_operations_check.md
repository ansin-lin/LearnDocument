# 第18章 部署与运行检查

> 本章目标：理解Spring Boot项目从开发环境部署到服务器的基本流程，认识Linux、运行配置、进程管理、健康检查、日志、发布和回滚，并能读懂常见部署手顺。

第17章已经在本机生成并运行了JAR。本章回答：把这个JAR交给服务器运行时要准备什么、怎样启动和检查、出现问题怎样调查。本章以Ubuntu 24.04 LTS为例讲概念，不要求学员拥有生产服务器管理员权限。完整操作参考见附录 [A18-1 Linux部署与运维手顺参考](../appendix/A18_01_linux_deployment_operations_reference.md)。

## 一、什么是部署

部署是把经过测试的应用版本放到指定运行环境，准备配置并启动，然后验证它能够提供预期服务。它不是简单复制文件：

```text
开发完成
   ↓
执行测试
   ↓
Maven打包
   ↓
准备服务器
   ↓
传输JAR并提供配置
   ↓
启动应用
   ↓
检查日志、接口和业务
   ↓
确认部署结果
```

每一步都有不同目的：测试降低回归风险；打包产生明确交付物；服务器提供长期运行环境；外部配置连接数据库；启动后还要用实际结果证明成功。

## 二、服务器需要哪些运行条件

| 条件 | 用途 | 缺少时的常见结果 |
| --- | --- | --- |
| 操作系统 | 管理文件、进程、网络和服务 | 应用无运行基础 |
| 兼容的Java | 执行JAR中的字节码 | 版本错误或无法启动 |
| 应用JAR | 第17章生成的程序 | 没有可运行应用 |
| 运行配置 | Profile、端口、数据库地址等 | 启动失败或连错环境 |
| 数据库连接 | 保存账号、员工和履历 | 业务查询或启动失败 |
| 端口 | 接收HTTP请求 | 客户端无法连接 |
| 日志位置 | 保存启动与运行信息 | 故障难以调查 |
| 运行进程 | 让应用持续执行 | 服务停止 |

配置和JAR是不同对象。同一个JAR可读取不同环境配置；数据库密码不能打进JAR或提交Git。

## 三、Linux与Java运行基础

Linux是服务器常见操作系统。Java应用能在Linux运行，是因为服务器上的JVM负责执行同一份Java字节码。部署前至少确认：

```bash
java -version
```

输出的Java版本必须与项目要求兼容。Linux路径使用 `/`，例如 `/opt/employee-api/employee-api.jar`，与Windows盘符路径不同。

在已获得授权的练习服务器上，最基本的前台启动形式是：

```bash
java -jar employee-api.jar --spring.profiles.active=prod
```

命令应在JAR所在目录或使用明确绝对路径执行，并由运行环境提供 `DB_URL`、`DB_USERNAME`、`DB_PASSWORD` 等必需值。前台运行适合观察启动日志和学习；关闭终端后进程可能结束，不适合作为长期生产运行方案。

文件权限决定运行账号能否读取JAR和配置、写入日志。生产服务不建议长期使用root运行，因为应用一旦被利用，root权限会扩大影响。创建账号、改所有者或权限属于受控管理员操作，主线不要求直接执行。

## 四、进程、端口与systemd

进程是正在执行的程序；端口是应用接收网络请求的入口。JAR文件存在不代表进程已经运行，进程存在也不代表端口已监听。

在授权的Linux练习环境中可认识：

```bash
ps
ss
```

`ps`查看进程，`ss`查看网络监听。具体参数、过滤和权限要求由项目手顺规定。

长期运行的Ubuntu服务常由systemd管理。systemd负责按配置启动、停止和监视服务；`systemctl`是与它交互的命令：

```bash
sudo systemctl start employee-api
sudo systemctl stop employee-api
sudo systemctl restart employee-api
sudo systemctl status employee-api
```

这些命令仅用于识别，不要在没有授权的服务器执行。服务名、权限和Unit文件由项目决定。完整Unit、运行账号和目录权限配置见A18-1附录。

## 五、如何判断部署是否成功

部署验证要分四层：

| 层次 | 要确认什么 | 典型证据 |
| --- | --- | --- |
| 进程 | Java程序是否仍在运行 | 服务状态或进程信息 |
| 端口 | 是否监听预期端口 | 端口监听信息 |
| HTTP | 健康接口能否响应 | `GET /health` 返回200 |
| 业务 | 登录、数据库和授权是否正常 | Postman业务场景结果 |

```text
Java进程运行
    ≠ 端口一定监听
    ≠ HTTP一定响应
    ≠ 业务功能一定正常
```

例如进程和 `/health` 都正常，但数据库凭据错误时，员工查询仍可能500。因此健康接口200只是基础证据。

### 简单验证案例

部署人员先确认服务状态和端口，再用Postman：

| 顺序 | HTTP方法与URL | 预期 |
| --- | --- | --- |
| 1 | `GET http://server:8080/health` | 200、`OK` |
| 2 | `GET /auth/csrf` | 200、取得令牌 |
| 3 | `POST /auth/login` | 200、建立Session |
| 4 | `GET /employees/1001` | tanaka本人查询200 |

登录请求必须按第15章携带CSRF令牌，后续请求保留同一Cookie；不能为部署验证关闭Security。真实服务器可能不允许直接访问应用端口，届时应按项目提供的正式URL验证。

## 六、日志与基本故障调查

第11章已经讲过Logger、requestId和异常记录。本章只使用日志调查部署问题：

```text
观察故障
   ↓
查看服务状态
   ↓
查看启动或应用日志
   ↓
确认配置、数据库或外部依赖
   ↓
定位并修复
   ↓
重新执行四层验证
```

### 场景一：服务无法启动

检查Java版本、Profile、必需环境变量、端口占用和启动日志。不能只反复restart而不阅读第一个根因。

### 场景二：数据库连接失败

检查数据库地址、账号、凭据是否由正确环境提供，以及服务器到数据库的网络条件。日志可以记录失败类型和目标环境标识，但不能打印密码。

### 场景三：接口返回500

保存请求时间、URL和requestId，在服务端日志中找到同一请求，判断异常发生在Controller、Service、Mapper还是数据库。修复后重测原场景及相关回归范围。

使用systemd时通常可通过项目授权的日志查看方式观察服务日志，例如：

```bash
sudo journalctl -u employee-api
```

该命令只表示常见入口；实际权限、时间范围和应用文件日志位置以项目手顺为准。

## 七、发布、回滚与日本项目流程

发布（リリース）是把经过确认的新版本部署到指定环境。回滚或切り戻し是在新版本造成严重问题时，按预先准备的方案恢复可用状态。

| 术语 | 含义 |
| --- | --- |
| リリース手順書 | 按顺序记录发布操作、负责人和确认点 |
| リリースチェックリスト | 防止漏项的发布检查清单 |
| 切り戻し手順 | 说明何时停止发布以及怎样恢复 |
| 障害対応 | 发生故障后的调查、沟通、修复与复验 |
| エビデンス | 命令结果、日志、响应等操作证据 |

发布前保留已知可用版本、外部配置备份和必要数据备份，是为了能够恢复。恢复旧JAR不等于数据库回滚：JAR是应用文件，数据库是另一份持久状态；新版本已经写入的数据不会因为替换JAR自动消失。涉及表结构或数据迁移时，必须在发布前评估向前兼容、备份和不可逆风险。

新人需要能读懂手顺、在授权范围内执行并保存证据，不要求独立设计生产发布计划。

## 八、常见问题

| 现象 | 可能层次 | 下一步 |
| --- | --- | --- |
| systemd显示失败 | 进程/配置 | 看启动日志和Java版本 |
| 进程存在但无法连接 | 端口/网络 | 核对监听端口和访问路径 |
| 健康接口200但员工接口500 | 数据库/业务 | 按requestId查应用日志 |
| 员工接口401 | 认证 | 检查是否已登录及Session |
| USER访问列表403 | 授权 | 对照第16章权限矩阵 |
| 新版本异常 | 发布 | 评估影响并按批准手顺切り戻し |

不要把所有故障都归因于“服务器问题”。先判断失败发生在进程、端口、HTTP、安全还是业务层。

## 九、理解任务与完成标准

1. 根据一段部署手顺，标出构建、配置、启动、四层验证和停止点。
2. 对“进程存在、健康接口200、员工查询500”写出调查顺序和需要保存的证据。
3. 说明为什么生产服务不长期使用root，以及为什么不能在无授权服务器运行sudo命令。
4. Review“替换旧JAR就等于数据库回滚”的说法，指出遗漏的数据库风险。
5. 用日语术语整理一张简短表：リリース、切り戻し、障害対応、エビデンス。

完成后，你应能解释部署与本地运行的区别、服务器运行条件、systemd作用、四层健康检查、日志调查、发布和回滚。复杂Linux权限、完整systemd Unit、多版本目录、摘要检查和详细恢复操作留到实际承担相关任务时查阅A18-1附录。

## 十、课程最终连接

第17章的结果是本机生成并验证过的JAR；第18章说明服务器如何接收这个交付物并提供长期服务。至此，Employee Management主线完成了：

```text
需求与分层 → Web API → 数据库与CRUD → 日志与测试
→ 事务与分页 → 登录与授权 → 配置与打包 → 部署与运行检查
```

真实项目还会根据组织制度增加代码审查、数据库迁移、监控、审批和自动化发布。本课程建立的是参与这些工作的基础，不把教学示例描述为完整生产方案。
