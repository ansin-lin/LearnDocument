# 07 日本项目改修与交付演习

日本项目中的 PG 经常不是从空文件开始，而是根据仕様、障害票或 Review 指摘修改已有脚本，并提交可复现的自测证据。本章模拟一次小型改修。

## 7.1 学员任务：开始状态

现有 `check_log.sh` 已完成第 6 章功能。收到以下改修票：

```text
件名：ログ抽出結果に調査情報を追加する

要件：
1. 成功输出的第一行增加执行时刻和输入文件名。
2. 日志明细仍保留原始行号。
3. 无匹配时不得创建新的正式结果文件。
4. 不得修改输入日志。
5. 既有退出状态保持不变。
```

这里的“既有”表示修改前已经存在的行为。改修不能只满足新要求，还要防止旧功能发生退化（デグレ，regression）。
动手前先用一句话写出：为什么改、会改哪一段、成功输出新增什么、哪些原有行为不能变、哪些输入可能失败、准备用什么证据证明结果。这相当于把仕様（规格）转成可检查的任务，不需要猜测隐藏要求。

## 7.2 修改前调查

先记录基线，而不是直接编辑：

```bash
bash -n check_log.sh
bash check_log.sh input/app.log R001
printf 'status=%s\n' "$?"
wc -l input/app.log output/R001.log
```

以上命令在 `~/learndoc-linux-lab` 中执行，无需 Git 仓库。`bash -n` 检查语法，不执行脚本；实际运行后立即记录状态；`wc -l` 分别显示原日志和已有结果的行数。任务记录要写明修改文件、调用方、输出格式变化及可能受影响的测试。已有 Git 练习仓库的学员可在仓库副本里完成同样调查，不要在真实项目仓库直接实验。

## 7.3 学员任务：实现要求

目标输出示意如下；执行时间应取**本次实际运行时刻**，不是把示例时间写死：

```text
executed_at=2026-09-01T10:15:00+0900 source=input/app.log
1:2026-09-01T09:00:00 INFO  request_id=R001 start
2:2026-09-01T09:00:01 ERROR request_id=R001 employee not found
```

注意：不能先创建正式文件再判断是否匹配，否则失败途中可能留下半份成果。路径仍需双引号引用，并沿用第 06 章的**完整 ID 字段匹配**，不能退回到只查字符串片段。请自己定位第 06 章中“搜索成功”和“发布正式结果”的代码段，只在必要位置改动；正文不提供完整改修答案。

## 7.4 学员任务：自测观点评审表

| 编号 | 观点评审 | 输入 | 预期 |
|---|---|---|---|
| T01 | 正常系 | `app.log R001` | 状态 0；头信息 1 行；明细 2 行 |
| T02 | 0 件 | `app.log R999` | 状态 1；不新建 `R999.log` |
| T03 | 文件不存在 | `missing.log R001` | 状态 3；stderr 可定位路径 |
| T04 | ID 格式错误 | `app.log 'R 001'` | 状态 2；不执行搜索 |
| T05 | 路径含空格 | `input/app copy.log R001` | 状态 0；结果正确 |
| T06 | 再执行 | 连续执行 T01 两次 | 结果没有重复追加 |
| T07 | 退化确认 | 比较输入文件前后校验值 | 输入内容未变化 |

执行 T05 前先运行 `cp -- input/app.log 'input/app copy.log'` 建立带空格的测试文件；双引号或单引号使整个路径作为一个参数。测试后可在确认路径后删除这个副本。执行 T02 前确认 `output/R999.log` 不存在；如果以前练习留下了该文件，先说明旧文件的处理方式，不把它当成本次新建结果。

“正常系”是正常流程，“异常系”是参数错误等失败流程，“境界值”是边界输入。自测不能只展示成功画面，还要覆盖这些代表性分支。

可用以下方式保存输入日志的前后证据：

```bash
sha256sum input/app.log > output/input.before.sha256
# 执行全部测试
sha256sum input/app.log > output/input.after.sha256
diff -u output/input.before.sha256 output/input.after.sha256
```

`sha256sum` 生成内容摘要；摘要相同可以作为文件内容未变化的证据。

## 7.5 交付材料（Git 为选做）

基础交付不要求 Git：保存修改后的 `check_log.sh`、T01～T07 的命令及输出、退出状态、输入文件摘要和未解决事项。另一名学员应能照记录复现。

如果已经在**单独的 Git 练习仓库**中完成脚本改修，再按 Git 课程的步骤检查并提交；没有仓库时跳过下面的命令，不在普通练习目录直接运行：

```bash
git status
git diff -- check_log.sh
bash -n check_log.sh
# 执行 T01～T07
git add check_log.sh
git diff --staged
git commit -m "fix: add investigation metadata to log result"
```

提交或 PR/MR 说明至少包含：

- 对应票号与改修目的
- 修改文件和影响范围
- T01～T07 的结果与退出状态
- 未执行项目及原因
- 已知限制，例如只支持 Bash 4 以上

Review 指摘対応时，回复“修改位置、修改理由、再测试结果”，不要只回复“已修复”。Git 的完整团队流程见[团队协作与代码评审](../git/06_teamwork_and_conflicts.md)。

## 7.6 夜间批处理障害的阅读题

另有一张障害票：「ジョブ `employee-import` が異常終了した（作业异常结束）」。手顺和模拟记录如下，不要求执行任何生产脚本：

```text
执行用户：batchuser
调用：bash import.sh input/employees.csv
结束状态：3
stdout：空
stderr：ERROR input missing: input/employees.csv
后续ジョブ：等待确认
```

先按「作业手顺 → 参数 → 输入文件 → 状态码 → stdout/stderr → 输出文件 → 后续依赖」逐项整理。可以确认脚本报告输入缺失并返回 3；但仅凭这份记录，不能判断文件为何缺失、是否已有部分数据写入、能否安全再执行。**再実行（重跑）可能导致重复导入、重复发送或重复更新**，必须先核对脚本的重复执行特性、业务影响和负责人批准。交付说明中把已确认事实、原因候选和残課題分开。

## 7.7 验收标准

- 新要求和既有行为都有测试证据。
- 修改仅限任务需要的文件，没有混入格式化或无关改动。
- 另一名学习者可以根据说明复现测试。
- 输出不含秘密信息、个人信息或整段生产日志。
