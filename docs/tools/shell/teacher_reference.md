# 教师参考：销售日次取込 Batch 改修 Review

仅供授课与评审。学员先根据[第 8 章详细设计与改修票](08_batch_project_practice.md)修改 `starter_run_sales_import.sh`，提交脚本与 T01～T07 证据，再对照[完整参考脚本](sample/sales-import/run_sales_import.sh)。

## 评审顺序

1. 先看执行顺序：参数数量、八位格式与真实日历日、输入存在/可读/非空、JAR 是否在位、同名归档冲突，都要在 Java 前完成。`20260230` 必须拒绝。
2. Java 用同步 `java -jar` 调用，`$?` 立即保存。Java 非 0 时不出现 `SUCCESS`、输入仍在原位置、日志含错误，Shell 返回约定的 10。不得只看日志文字。
3. 只有 Java 成功后才能 `mv` 归档；归档失败必须返回非 0。旧归档应保持不变，输入也不能被覆盖。
4. `T01` 核对 `rows=2`、归档文件内容和状态 0；`T02～T06` 核对各失败阶段及输入/归档不变量；`T07` 核对再执行不能被误报为成功。
5. 测试证据必须保存实际命令、即时读取的退出码、对应日志、文件状态与预期/实际。`ls` 检查缺失输入时自身非 0 不应混淆为脚本状态。
6. 检查编码、LF 换行、含空格路径的引用、固定目录与日志写入错误。生产环境的执行权限与调度配置不属于此练习。

## 参考答案边界与常见指摘

参考脚本是教学用的可运行实现，不是生产模板。它用 `date -d` 依赖 GNU date，模拟 Java 只做简化 CSV 校验与计数；没有数据库事务、并发互斥、完整 CSV 引号处理、运行中断恢复，也不能证明真实 Spring Batch 的幂等性。`tee` 或日志写入异常、Java 成功而归档失败时的再执行策略，均须按项目规格讨论。学员实现方式不同但满足可观察规格时可通过。

典型 Review 指摘：

- “Java 失败后仍移动 CSV”：要求学员追踪返回码分支并补 T05，而不是直接替其重写。
- “正常日志存在便认定成功”：要求展示 Shell 退出码、归档状态和 Java 输出三项证据。
- “T01 连续两次都期待 0”：指出第一次已移动输入，第二次起点不同；要恢复个人副本或作为再执行用例。
- “Java 错误状态被 `printf` 覆盖”：把状态保存移到外部程序后一行，复测 T05。

结课复核：能说明正常系、异常系、単体テスト（单体测试）、結合テスト（结合测试）、デグレ（退化）、エビデンス（证据）、シェル改修与リラン（重跑）的含义；能把已确认事实、原因候选、未验证风险分开汇报。
