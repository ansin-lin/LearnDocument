# 06 日志查看与调查

日志调查的目标不是找到所有 `ERROR`，而是在明确环境和时间范围后，找到与现象相关的证据并区分症状与根因。

## 6.1 先确认调查条件

开始前记录：环境、主机、时间范围、现象、request ID 或批处理 ID、允许访问的日志路径。日志可能位于项目目录、容器平台或 systemd journal，不假定全部在 `/var/log`。

本章使用 `~/learndoc-linux-lab/input/app.log`。
测试人员报告 `R001` 请求失败时，按“确认测试环境和报告时间 → 找到该环境日志 → 查 R001 → 看错误上下文 → 记录事实与未知项”的顺序调查。环境先确认，是为了不把另一台服务器的日志误当证据；时间先确认，是为了不把同号但不同时间的事件混在一起。
**日志**是程序运行时留下的记录；一行通常包含时间、级别、请求标识和事件。`INFO` 记录正常经过，`WARN` 表示值得注意，`ERROR` 表示出现错误。看到 `ERROR` 也不能直接断定根因，需要结合前后记录和同一个 request ID。
request ID 是一次请求的标识，同一个请求在不同处理步骤中写出的日志可用它串起来；批处理项目常用类似的 job ID。标识的具体格式由项目规定，不能只凭相近字符判断是同一请求。

## 6.2 分页和末尾查看

```bash
cd "$HOME/learndoc-linux-lab"
less input/app.log
tail -n 100 input/app.log
```

实时复现时可以使用 `tail -f`，完成后按 `Ctrl+C`。调查既有故障时优先限定时间和行数，避免无目的持续跟踪。
`less` 逐页查看，按 `q` 退出；`tail -n 100` 显示最后 100 行，不会修改日志。日志持续增长时，`-f` 会跟随新写入的内容；只在明确需要观察新事件时使用。

## 6.3 按标识和时间过滤

```bash
grep -n 'request_id=R001' input/app.log
grep -En 'ERROR|WARN' input/app.log
grep '2026-09-01T09:00' input/app.log
grep -n -C 1 'ERROR' input/app.log
grep -n -F 'request_id=R001' input/app.log
```

`grep -n` 显示匹配行及原文件行号；`-E` 让 `ERROR|WARN` 表示两种级别任选一种。第三条把时间缩到 `09:00` 这一分钟。命中前先核对日期、时区、环境与请求编号，不能把别的请求的错误算进本次调查。
样例的 R001 查询会得到第 1 行 `start` 和第 2 行 `employee not found`；行号让同伴能回到原日志核对。时间查询会同时出现这两行，不能仅凭时间把其他请求排除。前后文有助于观察处理顺序，但 `ERROR` 仍可能只是上游输入错误的表现。
`-C 1` 把 ERROR 的前后各 1 行一起显示；练习日志只有 4 行，实际长日志可按调查范围使用 `-C 5`。`-F` 将 `request_id=R001` 当普通文本查，不把符号解释成正则；但它也会命中 `R0012` 这样的前缀，必须结合实际日志字段边界核对。先按时间范围缩小调查，再按 request ID 串联同一次请求，最后看错误附近的记录；单独一个 ERROR 可能只是症状。

保存证据：

```bash
grep -n 'request_id=R001' input/app.log > output/R001-evidence.txt
wc -l output/R001-evidence.txt
```

预期有 2 行，能够看到请求开始和错误结果。

统计指定级别时可以运行 `grep 'ERROR' input/app.log | wc -l`，样例结果为 1；这只统计匹配文本的行数，不代表有 1 个独立故障。需要按级别汇总时可先提取固定的级别字段，再 `sort | uniq -c`；不要未经脱敏就复制整份业务日志。

### 日志轮转（了解）

持续写入的日志会变大，项目可能把旧文件改名为 `app.log.1`，新记录再写入新的 `app.log`，旧文件也可能被压缩。调查历史事件时先确定当时对应哪份文件。实时跟随时，`tail -f` 默认跟随已打开的文件，轮转后可能仍看旧文件；GNU `tail -F` 按文件名重开，适合某些轮转场景。二者按 `Ctrl+C` 停止；本课程不配置轮转程序。

## 6.4 journalctl 只读调查

环境使用 systemd 且当前用户有读取权限时：

```bash
journalctl --since '10 minutes ago' --no-pager | tail -n 50
journalctl -u <unit-name> --since '2026-09-01 09:00:00' --until '2026-09-01 09:10:00' --no-pager
```

`<unit-name>` 必须来自项目手顺。权限不足、没有 systemd 或日志保存在其他平台时，记录条件并使用项目指定方法；本课程不要求启停服务。
`journalctl` 读取 systemd 管理的日志；`--since`、`--until` 限定时间，`-u` 限定已知服务名，`--no-pager` 直接输出文字。第一条再用 `tail -n 50` 只显示最后 50 行；没有这些环境条件时跳过，不需为了练习寻找或创建系统服务。
systemd 是部分 Linux 环境中负责启动和管理系统服务的软件；本章只读取它保存的日志，不学习服务管理命令。

## 6.5 调查结果模板

在 `output/investigation.md` 中记录：

```markdown
# 调查结果

- 环境/主机：
- 调查时间范围：
- 现象：
- 使用命令：
- 确认结果：
- 根因判断：
- 影响范围：
- 暂定对策：
- 未确认事项（残课题）：
- 证据文件：
```

只写日志能直接支持的结论；推测要明确标成“推测”或“未确认”。公开证据前删除个人信息、访问令牌和业务敏感数据。
例如“样例日志在 09:00:01 记录 `employee not found`”是**已确认事实**；“员工记录不存在导致请求失败”需要更多应用或数据证据，暂列**原因候选**；“其他请求是否受影响”没有数据时应列为**未确认事项（残課題）**。

## 6.6 常见失败

- 路径不存在：先确认项目规定和当前环境，不遍历整个服务器猜日志位置。
- `Permission denied`：记录 `ls -l` 和当前身份，请负责人授权，不自行改权限。
- 搜不到 ERROR：检查时间、大小写、request ID、日志轮转和目标环境。
- 日志过大：使用 `less`、`tail` 和限定条件，不用 `cat` 打印全部内容。
