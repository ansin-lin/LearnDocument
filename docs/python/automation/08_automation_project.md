# 第8章 日本项目常见自动化项目

这一章不只放一个综合项目，而是给出 3 类日本项目高频自动化项目入口：

1. 自动化报表项目
2. 日志分析与异常提取项目
3. 运维辅助脚本项目

三类项目的共通目标都是一样的：

- 可重复执行
- 有明确输入输出
- 出错时可追查
- 支持补跑或重试

## 8.2 项目一：自动化报表项目

这是日本项目里最常见的业务自动化场景之一。

典型流程：

```text
数据库或接口 -> 数据整理 -> Excel 报表 -> 邮件或通知 -> 日志记录
```

### 适用场景

- 每日销售报表
- 月度库存报表
- 对账结果汇总表
- 部门运营日报

### 项目目标

假设你要做一个“每日销售报表自动生成脚本”，要求如下：

1. 接收处理日期。
2. 读取指定日期的数据。
3. 生成 Excel 报表。
4. 输出到固定目录。
5. 记录日志。
6. 失败时支持补跑。

### 建议目录结构

```text
daily_report_job/
├── input/
├── output/
├── archive/
├── logs/
├── config/
└── report_job.py
```

### 建议输入输出

输入可以来自：

- CSV 文件
- Excel 文件
- 数据库查询结果
- API 返回值

输出至少包括：

- 一份 Excel 报表
- 一份运行日志
- 必要时一份 CSV 中间结果

### 实现步骤

1. 接收 `--target-date` 参数。
2. 检查输入数据是否存在。
3. 读取数据并做最小整理。
4. 生成报表文件名，例如 `daily_report_20260723.xlsx`。
5. 输出 Excel 结果。
6. 记录开始、结束、成功、失败状态。
7. 成功后按需要归档原始文件。
8. 最后发送通知或保留通知接口。

### 最低验收标准

1. 脚本可以通过参数指定处理日期。
2. Excel 文件可以正常生成。
3. 输出目录、日志目录明确。
4. 失败时能定位问题。
5. 重跑时不会无提示覆盖重要结果。

## 8.3 项目二：日志分析与异常提取项目

这是现场排障和异常调查里非常高频的一类自动化任务。

典型流程：

```text
扫描日志目录 -> 筛选 ERROR/WARN -> 提取时间、错误码、编号 -> 输出结果文件 -> 记录日志
```

### 适用场景

- 从应用日志中提取错误记录
- 汇总每天异常件数
- 根据错误码分类统计
- 抽取需要上报的问题清单

### 项目目标

假设你要做一个“每日异常日志提取脚本”，要求如下：

1. 扫描指定目录中的日志文件。
2. 只抽取 `ERROR` 和 `WARN` 行。
3. 提取时间、错误码、业务编号等关键信息。
4. 输出异常清单。
5. 保留执行日志。

### 建议目录结构

```text
log_analysis_job/
├── input/
├── output/
├── archive/
├── logs/
└── log_job.py
```

### 建议输入输出

输入：

- 单日日志文件
- 某目录下多份日志文件

输出：

- `error_summary.csv`
- `error_details.csv`
- 执行日志文件

### 实现步骤

1. 扫描日志目录中的全部目标文件。
2. 逐行读取日志。
3. 用字符串判断或正则提取错误信息。
4. 把结果整理为结构化表格。
5. 输出为 CSV 或 Excel。
6. 记录异常文件、编码失败或格式异常。

### 最低验收标准

1. 能扫描多份日志文件。
2. 能提取错误时间、错误码或业务编号。
3. 输出结果文件可供人工复核。
4. 异常文件或编码问题不会导致整批静默失败。

### 本项目主要复用哪些前置章节

## 8.4 项目三：运维辅助脚本项目

这类项目不一定直接生成业务报表，但在日本项目现场同样非常常见。

典型流程：

```text
检查目录或任务状态 -> 汇总结果 -> 输出状态清单 -> 必要时通知 -> 记录日志
```

### 适用场景

- 批量检查文件是否到达
- 检查日报结果是否已生成
- 汇总某目录下失败文件
- 对指定日期任务执行补跑
- 生成执行状态清单

### 项目目标

假设你要做一个“文件到达与执行状态检查脚本”，要求如下：

1. 检查目标目录或目标文件。
2. 输出成功、失败、缺失对象清单。
3. 对异常对象单独记录。
4. 必要时发送通知。
5. 支持指定日期补跑检查。

### 建议目录结构

```text
ops_support_job/
├── input/
├── output/
├── logs/
├── config/
└── ops_job.py
```

### 建议输入输出

输入：

- 目标目录
- 配置文件中的应到文件清单
- 指定日期或指定批次

输出：

- `status_report.csv`
- `missing_files.csv`
- 控制台状态摘要
- 日志文件

### 实现步骤

1. 读取配置中的检查对象列表。
2. 检查文件、目录或任务状态。
3. 汇总成功、失败、缺失项目。
4. 输出状态清单。
5. 对异常对象单独记录日志。
6. 必要时调用接口或通知服务。

### 最低验收标准

1. 能明确列出成功、失败、缺失对象。
2. 能输出结果文件或控制台状态清单。
3. 支持最小补跑能力。
4. 失败时有日志可追查。

### 本项目主要复用哪些前置章节

- 目录和文件检查：见 [第2章](02_file_operations.md)
- 参数化执行：见 [第6章](06_batch_schedule.md)
- 日志与异常处理：见 [第7章](07_logging_retry.md)
- 接口通知：见 [第5章](05_requests_api.md)

## 8.5 三个项目怎么安排学习顺序

建议按下面顺序推进：

1. 先做自动化报表项目
2. 再做日志分析与异常提取项目
3. 最后做运维辅助脚本项目

原因是：

- 自动化报表最贴近业务交付
- 日志分析最贴近排障任务
- 运维辅助最能体现脚本稳定性和可维护性
