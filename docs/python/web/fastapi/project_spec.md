# 员工管理API项目规格

课程将逐步实现一个员工管理后端。开始编码前先确认数据、规则和验收条件；后续章节修改实现方式时，接口中的业务含义保持不变。

## 一、核心数据

| 业务对象 | 字段 | 规则 |
| --- | --- | --- |
| `Department` | `id`、`name` | 部门名称唯一 |
| `Employee` | `id`、`employee_number`、`name`、`department_id`、`email`、`joined_on`、`is_active` | 员工编号唯一，员工必须属于已有部门 |
| `UserAccount` | `id`、`login_id`、`password_hash`、`role_code`、`is_active` | 登录账号唯一，只保存密码哈希；角色代码使用权限表中的固定值 |

## 二、初始数据

| 员工编号 | 姓名 | 部门 | 邮箱 | 入职日期 | 在职 |
| --- | --- | --- | --- | --- | --- |
| `E001` | 山田太郎 | 开发部 | `yamada@example.com` | `2026-04-01` | 是 |
| `E002` | 佐藤花子 | 营业部 | 空字符串 | `2025-10-01` | 是 |

数据库至少包含开发部和营业部。练习创建的`E003`、`E010`不属于固定初始数据，进入下一阶段前应按章节要求清理或设置为离职。

## 三、业务规则

- 员工编号创建后不能修改。
- 多名员工可以属于同一部门。
- 员工引用的部门不能直接删除。
- 删除员工采用逻辑删除，只把`is_active`修改为`False`。
- 默认列表、详情、修改和删除只处理在职员工。
- 列表支持按姓名和员工编号进行关键字查询。
- 列表返回当前页数据、页码、每页数量和筛选后的总件数。
- 请求校验和Service判断不能代替数据库唯一约束与外键约束。

## 四、权限规则

| 角色 | 查询员工 | 新增、修改员工 | 删除员工 |
| --- | --- | --- | --- |
| `VIEWER` | 允许 | 拒绝 | 拒绝 |
| `HR_STAFF` | 允许 | 允许 | 拒绝 |
| `SYSTEM_ADMIN` | 允许 | 允许 | 允许 |

未登录请求员工接口时返回`401`；已经登录但角色权限不足时返回`403`。CORS设置和前端是否隐藏按钮都不能代替后端权限判断。

## 五、接口范围

| 方法 | 路径 | 主要结果 |
| --- | --- | --- |
| `GET` | `/health` | 返回应用健康状态 |
| `POST` | `/api/auth/token` | 验证账号并签发Bearer Token |
| `GET` | `/api/departments` | 返回部门列表 |
| `GET` | `/api/employees` | 返回在职员工分页列表 |
| `GET` | `/api/employees/{employee_number}` | 返回员工详情或`404` |
| `POST` | `/api/employees` | 新增成功返回`201`，编号重复返回`409` |
| `PUT` | `/api/employees/{employee_number}` | 修改允许编辑的字段 |
| `DELETE` | `/api/employees/{employee_number}` | 管理员逻辑删除，成功返回`204` |

## 六、最终验收

完成课程后应能证明：

1. 可以从空数据库执行迁移并生成初始数据。
2. 员工CRUD、搜索、分页和逻辑删除符合规格。
3. 重复员工编号、无效部门和不存在员工返回明确错误，失败事务不会留下部分数据。
4. 未认证请求、权限不足请求和禁用账号均被拒绝。
5. 测试使用隔离数据库，可以重复执行且不污染开发数据。
6. README能够指导另一名开发者完成配置、迁移、启动、测试和停止。
