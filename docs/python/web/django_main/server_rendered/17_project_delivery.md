# 第17章 项目整理与交付

## 本章成果

另一名开发者只阅读仓库说明，就能重新创建环境、启动系统、运行测试并完成验收。

## 本章开始状态

功能与测试已经完成。本章不增加业务功能，而是整理依赖、配置入口、忽略规则、重建步骤、运维边界和交接资料。可用[第18章服务端渲染参考项目](reference_project.md)核对交付物组成。

## 交付目录

- **交付是什么**：把代码、配置说明、依赖、迁移、测试和操作手顺整理成他人可重建、可验证的成果。
- **为什么需要**：开发者本机能运行不代表其他成员或目标环境能够运行，隐含步骤会在接收和发布时变成风险。
- **什么时候执行**：功能完成后、Review 前和发布前都要检查；项目交接时由接收方重新验证。

```text
源代码与迁移
→ 依赖与环境变量说明
→ 干净环境重建
→ check / test
→ 发布手顺
→ 健康检查与监控
→ 验收 / 回滚判断
```

应保留源代码、模板、Static、迁移、测试、依赖文件和 README；不提交虚拟环境、缓存、日志、本地数据库、上传附件和秘密配置。

`.gitignore` 至少考虑：

```gitignore
.venv/
__pycache__/
*.py[cod]
.env
db.sqlite3
media/
*.log
```

是否提交 SQLite 数据库由项目约定决定，本课程默认不提交。

`.gitignore` 中每一行表示不纳入版本管理的本机或运行时文件。它只阻止尚未跟踪的文件；已经提交过的密钥不会因为后来加入 `.gitignore` 就从历史中消失。

## 固定依赖和配置入口

课程基线使用 `Django>=5.2,<5.3`。团队项目还应采用约定的锁定方式保证可重复安装。秘密信息通过环境变量或密钥服务提供，README 只列变量名和示例，不写真实值。

README 至少包含：

1. 项目用途与主要功能。
2. Python、Django 和数据库版本基线。
3. 创建环境、安装依赖、迁移、创建账号、启动命令。
4. 测试和代码检查命令。
5. 必需环境变量与示例值。
6. 已知限制和验收步骤。

## 从零重建演练

在一个全新目录或干净环境中按 README 执行：安装依赖、配置环境变量、`migrate`、创建管理员、启动、运行测试。原开发目录能启动不等于项目可交付。

重建人员不得复制开发者的 `.venv`、`db.sqlite3` 或 `.env`。如果缺少这些文件就无法启动，说明依赖或配置说明仍不完整。

## 发布前检查

```bash
python manage.py check
python manage.py check --deploy
python manage.py test
python manage.py showmigrations
```

`check --deploy` 给出的是安全配置提示，需结合实际部署环境处理。生产还需确认 `DEBUG=False`、`ALLOWED_HOSTS`、HTTPS、安全 cookie、Static/Media 服务、备份与回滚方案。

这组命令分别检查 Django 配置、生产安全建议、自动测试和迁移执行状态。执行结果应记录命令、环境、时间和通过情况；仅写“确认完毕”不足以让接收方复现。

| 命令 | 参数 | 可接受的值与必填性 | 执行结果与时机 |
|---|---|---|---|
| `check` | 无 | 不接业务参数 | 检查当前配置；开发中和提交前执行 |
| `check --deploy` | `--deploy` | 可选开关；本次必须使用 | 输出生产安全警告；发布准备时执行，但通过不等于部署一定安全 |
| `test [test_labels]` | 测试标签 | App、模块、类或方法标签，可选 | 建立测试数据库并输出全量或指定测试结果；交付前执行全量 |
| `showmigrations [app_label]` | App标签 | 可选；省略时显示全部App | 输出各迁移是否已应用；发布前与发布后核对 |

## 现场识读：依赖、数据和静态资源的交付边界

`pip freeze` 会列出当前环境全部包，适合调查，不等于始终是最佳依赖设计。项目应明确直接依赖、允许版本范围和锁定方式，并在干净环境验证。`.env.example` 只提供变量名和安全示例，真实秘密不进入仓库。

`python -m pip freeze` 不传参数时把当前环境已安装包及版本写到标准输出，不修改依赖文件；用于调查或生成候选清单时执行，输出必须人工审查，不能直接代表项目全部直接依赖。

fixture 可用 `dumpdata`/`loaddata` 交换受控初始数据，但不要把生产个人信息直接导出到教学或测试环境。参考数据、迁移中的数据初始化、测试工厂各有用途，团队应明确谁负责创建哪些数据。

`python manage.py dumpdata [app_label.ModelName]` 将指定或全部数据库对象序列化到标准输出；范围参数可选，实际保存时还需使用受控输出文件。`python manage.py loaddata fixture_name` 的fixture名称必填，会把数据写入当前数据库。两者执行前都要确认环境、数据范围、个人信息、主键冲突和恢复方法。

```powershell
python manage.py collectstatic --noinput
```

`collectstatic` 把各App和配置目录中的静态文件收集到 `STATIC_ROOT`，不负责私有Media。`--noinput` 表示不进行交互确认，适合自动发布；执行结果会创建或覆盖收集目录中的文件。运行前必须正确设置 `STATIC_ROOT`，发布流程中在应用切换前执行，并确认旧文件清理和缓存策略。

## 发布与回滚说明

交付记录应写清迁移是否可逆、部署顺序、健康检查、监控观察点和回滚条件。代码回滚不一定能回滚数据库结构或已写业务数据；不可逆迁移必须在执行前准备备份和前向修复方案。README 之外，现场通常还需要发布手顺、测试证据和已知问题。

验收不能只看进程启动：使用真实角色确认登录、列表、CRUD、权限、附件、错误页和日志关联，并确保全新环境按说明可重建。

## 现场识读：多环境配置与真实数据库

本地 SQLite 适合学习，但测试、预发布和生产通常使用团队指定的 PostgreSQL 或 MySQL。进入项目后先确认 settings 的拆分方式、环境变量、数据库驱动和连接参数，不要把本地配置直接复制到生产。

下面是 PostgreSQL 配置片段，不是当前 SQLite 项目的替换步骤；使用时还需把团队指定版本的 `psycopg` 写入依赖文件：

```python
import os


DATABASES = {
    "default": {
        "ENGINE": "django.db.backends.postgresql",
        "NAME": os.environ["DB_NAME"],
        "USER": os.environ["DB_USER"],
        "PASSWORD": os.environ["DB_PASSWORD"],
        "HOST": os.environ["DB_HOST"],
        "PORT": os.environ.get("DB_PORT", "5432"),
        "CONN_MAX_AGE": 60,
    }
}
```

生产必填配置应缺失即启动失败，不能给生产密钥和数据库密码设置“不安全但能跑”的默认值。`settings/base.py`、`settings/development.py`、`settings/production.py` 是一种常见组织方式，但应遵守既有项目约定。

配置中的 `ENGINE` 选择数据库后端；`NAME`、`USER`、`PASSWORD`、`HOST` 和 `PORT` 来自部署环境；`CONN_MAX_AGE` 控制连接复用时间。示例使用 `os.environ[...]`，缺少生产必填变量时会立即失败，避免系统带着错误默认值启动。

`os.environ[key]` 的键必填，存在时返回字符串，不存在时抛出 `KeyError`；适合生产必填配置。`os.environ.get(key, default=None)` 的键必填、默认值可选，不存在时返回默认值；只用于确实允许默认值的配置。环境变量不会自动验证类型，整数、布尔或列表配置还需要显式转换和校验。

## 从 `runserver` 到生产请求链

```text
浏览器
→ HTTPS/反向代理
→ WSGI 或 ASGI 应用服务器
→ Django
→ PostgreSQL/MySQL、文件存储和其他服务
```

`runserver` 只用于开发。发布手顺至少说明安装锁定依赖、加载生产配置、执行兼容迁移、收集 Static、重启或切换应用、执行健康检查、观察日志指标以及满足什么条件时回滚。应用代码回滚、数据库回滚和文件存储恢复是三个不同问题。

## 本章总结

可交付项目必须能在干净环境重建，并明确依赖、配置、迁移、Static、Media、测试、健康检查和回滚边界。下一章不再增加新的 Django 业务 API，而是模拟日本 SES 现场的一次完整改修和交接。

## 日本项目中的实际使用

日本项目常把环境构筑手顺、发布手顺、单体测试证据和既知问题作为交付物。交付方说明操作，接收方实际重建，所有需要口头补充的步骤都应回写文档。发布前还会确认担当者、执行窗口、监控点和切戻し条件。

## 新人常见错误

- README 只写启动命令，没有说明版本、环境变量、迁移和测试。
- 把 `.venv`、本地数据库、上传文件或真实 `.env` 一起提交。
- 只在原开发目录验证，没有执行干净环境重建。
- 把 `check --deploy` 的提醒全部忽略，或误认为没有提醒就等于可安全上线。
- 认为代码回滚会自动恢复数据库和上传文件。
