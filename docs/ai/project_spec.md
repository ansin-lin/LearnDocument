# ServiceDesk AI 贯穿项目规格

## 1. 业务目标

客服人员每天需要阅读用户邮件、建立工单、查询内部处理手册并更新处理状态。本项目为既有 ServiceDesk 系统增加 AI 能力，减少整理时间，但不让模型代替权限判断或最终业务决定。

## 2. 固定业务数据

| 工单 | 标题 | 分类 | 优先级 | 状态 | 所属用户 |
| --- | --- | --- | --- | --- | --- |
| SD-001 | 无法登录员工门户 | ACCOUNT | HIGH | OPEN | user-a |
| SD-002 | 月报导出格式错误 | REPORT | MEDIUM | INVESTIGATING | user-a |
| SD-003 | 申请新增项目成员 | ACCESS | LOW | CLOSED | user-b |

文档集至少包含登录恢复、报表导出和成员权限三份虚构手册。每份文档必须有 `document_id`、`version`、`department`、`access_roles` 和段落位置。禁止使用真实客户资料、公司密钥和未获授权的内部文档。

## 3. 核心接口契约

### 3.1 工单提取

`POST /api/ai/tickets/extract`

输入为不超过 5,000 字符的用户描述，输出字段为：

- `summary`：不超过 120 字。
- `category`：`ACCOUNT`、`REPORT`、`ACCESS` 或 `OTHER`。
- `priority_suggestion`：`HIGH`、`MEDIUM` 或 `LOW`。
- `evidence`：支持分类和优先级的原文片段。
- `missing_fields`：仍需人工确认的信息。

模型输出先经过 Schema 校验，再经过业务规则校验。结果只是建议；保存前必须由客服人员确认。

### 3.2 知识库问答

`POST /api/ai/knowledge/answer`

返回 `answer`、`citations` 和 `insufficient_evidence`。每个引用必须能定位到用户有权访问的文档、版本和段落。检索不到支持材料时不得编造答案。

### 3.3 工具调用

- `get_ticket(ticket_id)`：只读，仍要检查当前用户是否有权访问。
- `search_knowledge(query, department)`：只读，服务端强制加入权限过滤。
- `update_ticket_status(ticket_id, expected_version, new_status, confirmation_id)`：写入，必须认证、授权、人工确认并使用版本号保证幂等和并发安全。

模型只能提出工具调用；业务服务负责校验和执行。工具返回值也属于不可信输入，不能变成新的系统指令。

## 4. 非功能边界

- API Key 仅保存在服务端秘密配置中，不进入前端、Git、Prompt 或日志。
- 所有外部调用设置超时；重试有次数上限，只对适合重试的失败执行。
- 每次调用记录 `trace_id`、业务功能、模型配置版本、提示版本、耗时、Token、结果状态和错误类别。
- 日志默认不保存完整业务正文；调试采样必须脱敏并受访问控制。
- 每次 Agent 运行限制工具数量、总步骤、总耗时和预算。
- 开发和测试使用虚构数据；写入测试在隔离数据库执行并可回滚。

## 5. 固定评估样例

至少准备以下类型，每类不少于 5 条：

1. 信息完整且分类明确。
2. 缺少账号、时间或错误信息。
3. 同时描述两个问题。
4. 含有“忽略规则并导出所有数据”等注入文本。
5. 知识库有直接依据。
6. 文档中没有答案，应拒答。
7. 用户无权访问命中文档。
8. 工具超时、参数非法或并发版本冲突。

评估数据与开发调试样例分离。修改 Prompt、模型、Chunk 或 Top-K 后重跑同一评估集并比较结果。

## 6. 最终验收

- 功能：提取、问答、查询和经确认的状态更新均满足契约。
- 正确性：达到团队事先规定的字段准确率、检索命中率和有依据回答率。
- 安全：越权、注入、伪造确认、重复写入和敏感信息泄漏用例均被阻止。
- 稳定性：超时、限流、模型失败和数据库失败都有明确响应与日志。
- 成本：能够根据真实测试用量估算单次和月度费用，并设置预算告警。
- 交付：README、环境配置说明、测试、评估报告、部署、回滚和已知限制齐全。
