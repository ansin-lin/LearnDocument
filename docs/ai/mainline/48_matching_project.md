# 第 48 章 综合项目④：案件 × 技术者 AI 匹配

> 项目成果：实现可解释的候选匹配辅助，不让模型替代招聘或配置决定。

确定性条件如工作地点、可用日期、必需资格先由普通程序过滤；LLM 只处理技能表述归一、经验摘要和解释。最终评分公式、权重和阈值由业务规则管理并可审计。

## 数据与职责边界

案件包含必需/加分技能、地点、期间和语言要求；技术者资料包含经本人确认的技能与经历。LLM 只能从资料提取候选能力和解释匹配点，不能推断受保护属性、人格或健康情况。

## 实现步骤

1. 用确定性规则过滤不满足硬条件的候选。
2. 将技能名映射到受控词表，未知项进入人工确认。
3. 计算透明的规则分数，可选使用向量作为候选信号。
4. LLM 根据已确认字段生成理由和缺口，不自行改分。
5. 页面同时显示证据、缺失信息和人工决定。

## 评价与偏差

准备同能力不同表达、资料顺序变化、缺失字段和敏感属性干扰样例。比较排序稳定性、理由支持率和错误淘汰率。业务专家复核门槛，不能以历史决定直接当无偏真值。

## 必须验收

- 每个推荐理由能回到案件和技术者资料。
- 缺失信息显示为缺失，不推断年龄、性别、国籍等敏感属性。
- 比较不同表达、顺序和群体样例，检查不合理偏差。
- 人工可以查看依据、调整和拒绝建议。
- 不把相似度或模型自评分数当作客观胜任度。

使用完全虚构资料，提交错误案例、偏差检查和人工决策记录。

## 不应实现的功能

首版不自动录用或淘汰人员，不把受保护或无关属性用于评分，不让 LLM 直接修改候选人资料，也不隐藏匹配依据和规则版本。

## 匹配规则的分层

先用确定性条件做硬过滤，例如可工作地区、合同期间、必须资格和不可缺少技能；再用结构化特征和 Embedding 找候选；最后由 LLM 根据明确 Rubric 解释匹配点、缺口和待确认项。LLM 不直接决定录用或淘汰。

## 数据标准化

“Java 3 年”“Java：三年以上”和项目经历中的 Java 不能直接当作同一原始字符串比较。需要定义技能词表、经验时间计算、必需与希望条件、语言等级和可用日期。AI 可以抽取候选字段，但人要确认低置信和矛盾信息。

## 分步成果

1. 设计案件与技术者的结构化字段和数据来源；
2. 实现硬条件过滤并输出排除理由；
3. 加入语义候选召回和可调整的排序分数；
4. 生成引用原始经历的匹配说明与缺口；
5. 提供人工确认、反馈和审计记录；
6. 使用历史样本评价排序和群体差异。

## 公平性与可解释性

姓名、性别、年龄等与任务无关或受限制的属性不进入匹配提示和评分。检查不同群体的推荐率与错误类型，但统计差异不能自动证明公平或歧视，需要结合样本、业务规则和法律政策审查。

验收时必须能解释每个硬过滤、每项分数和每段 LLM 说明的来源；修改规则后可重放同一数据集并比较排序变化。

不自动拒绝人员、不生成未经证据支持的能力、不把模型自报置信度当概率、不将敏感属性放入评分。最终决定与责任属于授权业务人员。
