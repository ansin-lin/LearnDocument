# 第 44 章 AI 应用部署

> 本章成果：使用 Docker 和环境配置部署 AI 服务，并完成健康检查、监控和回滚演练。

构建镜像时不复制 `.env` 和 Key，使用非 root 用户、明确基础镜像版本和健康检查。运行时注入秘密；区分本地、测试、预发布和生产模型配置。

## 1. 构建与运行配置

锁定依赖并生成可追踪镜像标签；使用多阶段构建或最小运行镜像；以非 root 身份运行。Key、数据库密码和供应商配置在运行时注入，不进入镜像层和构建日志。

发布顺序包括构建与扫描、普通测试、AI 评估、数据库兼容检查、预发布验证、流量切换和监控。健康检查分为进程可用和业务就绪；不能因外部模型短暂失败就让整个业务系统不可诊断。

## 2. 健康与依赖

存活检查只判断进程；就绪检查确认必要本地依赖。外部模型故障可以让 AI 功能降级，但普通工单功能应按设计继续工作。不要在高频健康检查中产生付费模型请求。

## 3. 发布策略

在预发布用虚构数据运行普通测试、安全用例和评估集，再使用小流量或功能开关发布。监控错误、质量、延迟和费用，定义自动或人工回滚条件。

回滚必须考虑 Prompt、模型配置、数据库 Schema、向量索引和文档版本。先在隔离环境演练停止、回滚和恢复，再形成手顺。

## 4. 数据变更

数据库迁移和向量索引更新都要设计兼容、验证与回退。新索引并行构建并通过抽样评价后再切换，避免原地覆盖造成不可用。

## 5. Docker 镜像与运行配置

镜像包含应用和固定依赖，不包含 API Key、生产 `.env` 或用户文档。使用固定依赖版本、非 root 用户和最小运行文件；部署时从秘密管理与环境配置注入凭据。构建完成后扫描依赖和镜像，确认没有敏感文件。

## 6. Liveness 与 Readiness

Liveness 回答“进程是否还活着”，不应每次调用昂贵的模型；Readiness 回答“当前是否可以接收业务流量”，可检查关键本地依赖并谨慎处理外部服务状态。外部模型短暂波动时，系统可能仍可提供历史查询或降级功能。

## 7. 发布不是一次替换

先在测试环境用相同配置结构运行评估和冒烟测试，再采用滚动、蓝绿或小流量发布。观察错误率、质量、延迟和成本，而不只看容器是否启动。Prompt、模型和索引也属于发布版本，必须能追踪与回退。

## 8. 数据与索引迁移

数据库迁移先验证向前和回退路径；向量索引重建使用新版本并行生成，抽样和评估通过后再切换别名或有效标记。不要直接删除旧索引后原地重建，否则失败期间服务没有可用数据。

## 9. 上线检查

确认秘密未进入镜像和日志、健康检查合理、资源与并发受限、超时和重试有总预算、监控告警可用、备份已验证、回退步骤可执行。最后由另一名学员按运维手册完成部署和回退演练，证明文档不是只对作者有效。

数据库迁移采用前后兼容顺序；向量索引使用版本切换；Prompt 与模型配置可回退。不可逆操作必须有备份、验证和明确停机影响。

实践：构建不含秘密的镜像，部署假模型环境，制造新版本评估失败并回滚。记录实际命令、镜像标识、检查结果、日志位置和数据是否保留。
