# 第 9 章 AI 辅助 Coding

> 本章成果：使用 AI 调查、解释、生成和修改代码，将工作限制在已确认范围，并用差异、测试和实际行为验收。

## 1. AI 编码的四种任务

| 任务 | 适合用途 | 主要风险 |
| --- | --- | --- |
| 解释 | 梳理入口、调用链和数据流 | 根据名称猜测未读取代码 |
| 生成 | 创建独立函数、测试或样板 | 接口、版本和项目规范不匹配 |
| 修改 | 在现有工程完成小范围改修 | 扩大范围或破坏兼容性 |
| 调查 | 查找相关文件和影响范围 | 漏掉动态配置、SQL 或间接调用 |

## 2. 小步闭环

采用“建立基线 → 只读调查 → 提出计划 → 单点修改 → 查看差异 → 最小测试 → 相关回归”的循环。每一步都应留下可观察结果。复杂改修拆成多个能独立验证的小增量。

开始前记录当前分支、已有未提交改动和基线测试。用户已有改动不能被覆盖；未经授权不升级依赖、不改数据库结构、不全库格式化。

## 3. 让 AI 先解释调用链

以工单提取接口为例，要求回答：请求从哪个路由进入；Pydantic 在哪里校验；Service 怎样调用模型客户端；异常如何转换；结果由谁保存；有哪些测试。每个结论必须给出实际文件和符号。

只逐行翻译语法没有价值。若 AI 没有读取某个文件，就不能声称知道其中行为。

## 4. 可执行的修改 Prompt

```text
目标：为 description 增加 1～5000 字符校验。
依据：接口规格 AI-EXT-001 已确认。
开始状态：原有测试全部通过；工作区存在用户的 README 修改，不得覆盖。
允许修改：请求模型和对应测试。
禁止：改错误结构、数据库、依赖和无关格式。
先只读调查并列出实际位置；确认后再修改。
完成条件：0、1、5000、5001 用例符合规格，原有相关测试通过。
最终报告：差异、实际命令、退出结果、未验证事项。
```

## 5. 怎样检查代码差异

不要只看最终完整文件。逐块检查每一处新增、删除和移动：是否对应需求；是否改变公共接口；是否引入新依赖；异常是否被吞掉；日志是否含敏感内容；测试是否真的验证行为。

特别警惕 AI 为了“整洁”改名、抽象新层、格式化全文件或删除看不懂的兼容逻辑。无法解释的差异先撤出本次任务，而不是一并提交。

## 6. 测试证据

验证至少分为语法/类型或编译、受影响测试、相关回归和实际接口行为。测试命令、环境、测试数、通过失败和时间应真实记录。没有运行环境时明确写“未执行”，不能复制 AI 预计输出。

## 7. 错误做法对照

| 错误做法 | 后果 | 正确处理 |
| --- | --- | --- |
| 一次要求重构整个项目 | 差异巨大，难以定位回归 | 每次完成一个可测行为 |
| 直接粘贴报错让 AI 修 | 容易修症状 | 先复现并收集调用链 |
| AI 同时写实现和预期 | 测试迎合错误实现 | 预期来自已确认规格 |
| 只运行新增测试 | 旧行为可能被破坏 | 执行相关回归 |
| 接受“已经测试”文字 | 没有执行证据 | 查看真实命令和结果 |

## 8. 实践与验收

在练习副本为工单标题增加首尾空白清理，但保留中间空格。先让 AI 调查，再限定实现和测试文件完成修改。准备空字符串、只有空白、中间双空格和日文标题用例。

提交基线、Prompt、计划、最终差异和测试结果。验收时能解释每一行变化；故意删除清理逻辑后测试应失败；工作区原有无关修改保持不变。

## 9. 新人核对卡

AI Coding 的基本单位应是一个可验证的小修改：先读相关代码和规则，再说明计划，修改限定文件，查看差异，运行测试，人工复核。代码“看起来合理”不等于依赖存在、类型正确、异常已处理或与项目版本兼容。

当 AI 给出大面积重写时，先要求解释必要性并缩小范围。学员必须能回答修改前行为、修改后行为、影响文件、验证命令和剩余风险，不能把“这是 AI 生成的”作为无法解释的理由。
