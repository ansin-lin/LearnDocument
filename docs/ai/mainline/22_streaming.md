# 第 22 章 Streaming

> 本章成果：通过 SSE 展示增量文本，并正确处理开始、完成、取消和失败状态。

Streaming 改善等待体验，不提高答案正确性。服务端读取模型事件，只把允许的文本增量转换为 SSE；前端维护 `idle/loading/streaming/completed/error/cancelled` 状态。

## 1. SSE 的基本关系

浏览器建立一次 HTTP 连接，服务端持续发送事件。事件应有明确类型，例如 `delta`、`completed`、`error`，必要时携带事件 ID。SSE 是传输方式，不负责认证、会话一致性或结果校验。

连接断开时应停止下游读取或释放资源。不能在流尚未完成时把部分 JSON 当作合法结构化结果；需要结构化业务数据时优先等待完整响应并校验。

## 2. 服务端处理

检查模型事件类型，只转发允许的文本；累计使用量和完成状态；捕获取消并关闭下游流；错误后只发送一次终止事件。响应开始后通常不能再改 HTTP 状态码，因此错误事件契约必须提前设计。

## 3. 前端处理

逐段追加显示，但最终消息只有收到完成事件后才持久化。重复点击要取消旧请求或禁止提交；组件卸载时清理连接。对 Markdown/HTML 输出做安全渲染，不能把模型文本当可信脚本。

## 4. 验证

分别验证首个事件、文本增量、正常完成、错误、断线与取消。还要通过实际代理环境检查是否被缓冲，并确保并发请求不会把增量追加到错误消息。

## 5. Streaming 改变的是传输方式

非流式响应要等完整结果生成后一次返回；流式响应把生成过程中的事件逐步发送给客户端。它能降低用户感知的等待时间，但不会自动减少模型计算时间，也不会保证最终结果正确。

SSE 通常是服务端到浏览器的单向事件流，适合文字增量展示。WebSocket 支持双向长期通信，能力更强但连接管理更复杂。普通聊天逐字显示通常不需要为了“高级”而改用 WebSocket。

## 6. 不要把每个事件都当成文字

流中可能包含开始、文本增量、工具调用参数增量、完成、拒绝和错误等不同事件。后端要按事件类型解析；前端只把文本增量追加到消息区域，同时保存消息状态。收到完成事件后才能把结果标记为最终完成。

若中途断线，已显示的半句话不能冒充完整答案。界面应显示“连接中断，可重试”，服务端记录本次请求是否已完成以及供应商追踪编号。

## 7. 缓冲、取消和反向压力

代理服务器可能缓冲输出，导致服务端虽然逐段发送，浏览器仍一次收到。部署验证必须穿过真实代理链路。用户点击取消时，前端终止连接，后端也应尽量取消上游请求并停止继续保存增量。

如果客户端读取速度跟不上，服务端不能无限把事件堆在内存中；应限制缓冲区和单次响应大小。

## 8. 新人验收清单

验证首个字符延迟、中文字符没有乱码、完成事件只出现一次、断网后有明确状态、取消后不再增长、两个并发会话不会串流、错误内容不会以 200 完成态显示。测试日志应同时记录请求编号、开始、首事件、完成或失败时间，便于分析“总耗时”和“首字耗时”。

除正常增量外，测试首事件前失败、中途断开、重复事件、用户取消和完成后重连。记录首字节时间、总耗时和完成率，不只看“逐字效果”。

官方 Responses API 会产生不同类型的流事件，应用应按事件类型处理，不把所有事件都当成文本。参阅[官方 Streaming 指南](https://developers.openai.com/api/docs/guides/streaming-responses)。

实践：实现流式摘要页面，分别验证正常结束、用户取消、模型中途错误和重复点击。保存浏览器网络事件与服务端日志中的同一 `trace_id`。
