# 第 19 章 在 FastAPI 中接入 AI Service

> 本章成果：在已有项目中建立可替换、可测试的 AI Client 与业务 Service 边界。

业务路由不应到处直接调用供应商 SDK。定义项目自己的最小接口，例如 `generate_text(request) -> AIResult`，再由供应商适配器实现。`AIResult` 保存文本、模型、用量和供应商请求 ID；业务层只依赖项目接口。

## 1. 为什么需要适配层

供应商响应结构、异常和配置会变化。适配层把它们转换成项目稳定对象，使路由和业务规则不依赖 SDK 细节，也方便测试和替换实现。不要为了“通用”提前抽象所有供应商功能，只覆盖项目实际使用能力。

```text
Router → TicketAIService → LLMClient（项目接口）
                         ├─ OpenAIClient
                         └─ FakeLLMClient（测试）
```

异常也要转换为项目类型：超时、限流、认证失败、非法响应和暂时服务错误。不要把供应商原始错误或敏感请求内容直接返回前端。

## 2. 请求和结果对象

请求对象保存指令、输入、输出上限、业务功能和追踪信息；结果对象保存文本、完成状态、模型、Token 和请求 ID。密钥不属于业务请求对象。供应商原始响应只在适配器内解析。

## 3. 生命周期和并发

客户端通常由应用启动过程创建并复用，关闭时释放连接。调用必须有超时；并发上限由服务控制。不要在每个路由中重新创建客户端，也不要使用无限重试占满工作线程。

## 4. 测试边界

业务 Service 用 Fake Adapter 验证流程，AI Adapter 用契约测试验证供应商交互，API 层验证 HTTP 契约。这样能区分业务错误、适配错误和外部服务波动。

## 5. Controller、Service 与 AI Adapter 的区别

| 层 | 主要职责 | 不应承担 |
| --- | --- | --- |
| API/Controller | 解析 HTTP、认证、映射状态码 | 拼接供应商专用请求 |
| 业务 Service | 执行业务规则和流程 | 依赖某个 SDK 的响应对象 |
| AI Adapter | 隔离模型 SDK、超时、重试和结果转换 | 决定用户是否有权读取工单 |

这样分层后，替换模型供应商只影响适配层；业务测试可以使用 Fake Adapter；HTTP 层也不必理解模型事件格式。

## 6. 输入输出对象为什么必要

不要在系统内部到处传递任意字典。请求对象应明确任务输入，例如 `ticket_id`、清洗后的正文和输出语言；结果对象应明确摘要、置信提示、引用来源和调用追踪编号。供应商新增字段时，内部业务不会被意外影响。

模型返回的“看起来像 JSON 的文本”仍然是不可信输入。适配层先解析并做 Schema 校验，业务层再验证枚举、长度、工单状态等业务约束。

## 7. 超时、重试和重复请求

网络超时不代表供应商一定没有处理请求，因此重试可能重复计费或重复触发后续保存。只对明确可恢复的错误有限重试，并加入退避与总时间预算。涉及写操作时使用幂等键或业务唯一键，防止重复保存。

学员应为适配层至少测试：正常返回、认证失败、限流、超时、格式错误、内容拒绝和调用取消。每种错误需映射为系统自己的错误类型，不能把供应商原始异常直接泄漏给前端。

路由测试替换业务 Service；Service 测试替换 LLMClient；适配器契约测试使用脱敏固定响应；少量真实调用单独标记。这样可以判断失败发生在哪一层。

实践：增加一个不调用真实模型的 Fake Client，让 `/api/ai/health` 验证依赖装配。运行原有 API 测试和新增测试，证明断网时仍可完成自动测试。
