# 第 7 章 AI 使用风险

> 本章成果：能够识别幻觉、错误代码、敏感数据、Prompt Injection、过度授权和不可审计风险，并在使用 AI 前后执行可检查的防护步骤。

## 1. 风险来自整个系统

AI 风险不只来自模型回答。数据怎样进入服务、模型能调用什么工具、输出怎样进入数据库、日志保存什么内容，都会影响安全。即使 Prompt 写着“不要泄露”，前端暴露 Key 或后端缺少授权仍然不安全。

## 2. 六类核心风险

### 2.1 幻觉与错误事实

模型可能编造接口、版本、业务规则或执行结果。防护是提供依据、允许回答资料不足、连接权威数据并逐条核对，而不是要求模型“保证正确”。

### 2.2 错误或不安全代码

代码可能能运行，但存在 SQL 注入、越权、事务错误、无限重试或数据丢失。必须检查差异、运行测试、做安全 Review，并在隔离环境验证副作用。

### 2.3 敏感信息泄漏

常见敏感内容包括个人信息、客户资料、源代码、内部地址、访问令牌、数据库连接串和生产日志。是否允许发送取决于组织政策、合同与所用服务配置，不能因为工具“很常用”就默认允许。

### 2.4 Prompt Injection

用户、网页、邮件和知识库文档都可能包含试图改变系统指令或诱导调用工具的内容。不可信文本只能作为数据。真正防护依赖权限、参数白名单、网络与文件范围、人工确认和审计。

### 2.5 过度授权

给 Agent 一个“执行任意 SQL”或“读取任意文件”的工具，会把一次模型错误扩大成系统事故。工具应最小化；查询也要检查当前用户权限；写操作需要明确授权、确认和幂等。

### 2.6 无法审计

如果不知道输入版本、模型配置、Prompt、工具调用和实际结果，就无法复现错误。日志需要记录关联 ID 和必要元数据，但不能为了审计再次保存完整秘密。

## 3. 数据分级和处理

| 级别 | 示例 | AI 使用原则 |
| --- | --- | --- |
| 公开 | 已公开产品说明 | 可按批准工具使用，仍核对来源 |
| 内部 | 普通内部流程 | 依据公司政策和服务配置 |
| 机密 | 未公开代码、客户合同 | 默认不发送，需明确批准和最小化 |
| 高敏感 | Key、密码、身份数据 | 不进入 Prompt；使用安全配置和脱敏数据 |

脱敏不是简单删除姓名。还要处理邮箱、电话、地址、工单号映射、令牌、Cookie、内部域名以及能够重新识别个人的组合字段。

## 4. 使用前、使用中、使用后

### 使用前

确认工具是否获准；对数据分类；缩小输入；使用虚构或脱敏数据；明确允许操作和完成条件。

### 使用中

检查模型是否索取额外敏感信息；工具调用是否越界；是否出现未经确认的写操作；遇到冲突或高风险决定时停止。

### 使用后

核对事实、代码差异和执行证据；清理临时资料；检查日志与提交；记录模型无法验证的部分；发生泄漏时按组织流程报告，而不是只删除聊天记录。

## 5. 脱敏示例

原始日志：

```text
user=tanaka@example.com token=abc123-secret
POST https://internal.example.local/login trace=7f21 result=401
```

用于调查的版本：

```text
user=<USER_001> token=<REMOVED>
POST <INTERNAL_LOGIN_ENDPOINT> trace=7f21 result=401
```

保留 `trace` 和状态码有助于定位；Token 必须完全移除。若工单号也能关联真实个人，应改为稳定的虚构映射。

## 6. 风险判断案例

有人要求 AI：“读取共享盘所有客户合同，总结后发送给外部邮箱。”即使业务目标合理，也同时涉及大范围读取、机密数据和外部发送。合格处理应停止，确认授权、限定合同范围、确定批准工具、脱敏并把外部发送设为独立人工确认步骤。

## 7. 实践与参考标准

对一份包含姓名、邮箱、Cookie、内部 URL、堆栈、SQL 参数和 trace ID 的日志制作脱敏版，再写风险登记表：数据级别、潜在影响、现有防护、缺口、负责人和验证方法。

验收标准：秘密完全移除；保留定位所需的错误类型和关联信息；没有把 Prompt 当作权限控制；至少设计幻觉、越权、注入和日志泄漏四个失败用例。

## 8. 新人核对卡

安全不是“不要把密码发给 AI”这一条。还包括输入是否有权读取、供应商怎样处理数据、模型是否会泄漏上下文、工具是否能越权写入、日志是否保存敏感内容、失败是否造成费用或服务不可用。

最重要的原则是：Prompt 只能表达意图，权限必须由程序执行；模型输出是不可信输入；高风险动作必须经过服务端校验和必要的人工确认；发生事件后要能追溯、撤销或停止。
