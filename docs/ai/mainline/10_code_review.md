# 第 10 章 AI Code Review

> 本章成果：让 AI 辅助发现正确性、安全、性能和可维护性问题，并把候选意见转为有位置、有触发条件、有证据的 Review 指摘。

## 1. Review 不是让 AI 打分

“请检查这段代码有没有问题”缺少规格和上下文。AI 可能只评论命名，也可能把个人偏好当缺陷。有效 Review 需要需求、差异、相关调用链、数据结构、运行环境和测试结果。

AI 适合扩大检查视角和解释风险，最终结论仍由审查者用代码、规格、测试或官方资料验证。

## 2. 检查顺序

1. 需求和接口契约是否实现正确。
2. 认证、授权、输入输出、秘密和注入边界。
3. 数据一致性、事务、并发和幂等。
4. 异常、超时、重试、资源释放和日志。
5. 性能与成本是否有代表性证据。
6. 可读性、职责、重复和测试覆盖。

先检查高影响问题，再处理命名和格式，避免几十条风格意见淹没真正缺陷。

## 3. Review Prompt

```text
依据接口规格和本次差异进行 Review，不修改文件。
重点检查：正确性、安全、权限、异常、数据一致性、性能、测试。
每条候选问题输出：位置、严重度、触发条件、影响、证据、最小修正建议、验证方法。
不能从现有材料证明的内容标为“待调查”，不要作为确定缺陷。
忽略与本次差异无关的纯风格建议，除非它直接造成误解或风险。
```

## 4. 示例：直接保存模型结果

```python
async def create_ticket(user_text: str):
    result = await llm.extract(user_text)
    await repository.insert(result)
    return result
```

这是省略上下文的教学片段，不能直接运行。Review 时至少提出：输入长度是否校验；模型输出是否通过 Schema；分类和优先级是否符合业务规则；当前用户是否有创建权限；是否需要人工确认；写入是否在事务内；超时怎样处理；日志是否泄露正文。

但不能仅凭这几行断言“存在 SQL 注入”或“事务一定失效”，因为 `repository.insert` 的实现尚未提供。这类内容应标为待调查，并请求最小相关代码。

## 5. 指摘表

| 字段 | 写法 |
| --- | --- |
| 位置 | 文件、函数及尽可能精确的行 |
| 严重度 | P0 技术/安全错误；P1 核心缺失；P2 维护性问题 |
| 触发条件 | 哪个输入、权限或运行状态 |
| 影响 | 错误结果、泄漏、损坏或维护成本 |
| 证据 | 规格、代码路径、测试或实际日志 |
| 建议 | 最小可执行修正，不顺手扩范围 |
| 验证 | 修正前失败、修正后通过的检查 |

## 6. 验证 AI 指摘

先定位代码是否真实存在；追踪完整调用链；构造触发输入；运行现有测试或最小复现；确认严重度；再决定接受、驳回或转调查。AI 引用不存在的方法、过期 API 或假设框架默认行为时，用当前依赖和官方资料核对。

## 7. 处理误报与漏报

误报也要记录原因，例如上层已经校验、工具没有副作用或建议与项目版本不符。为重要风险准备 Review 清单和测试，不依赖一次 AI 审查发现所有问题。修改后重新审查差异，而不是默认指摘关闭。

## 8. 实践与参考判断

审查“模型提取结果经人工确认后保存”的改修。提供需求、差异、模型接口、Repository 和测试。先让 AI 输出候选指摘，再人工验证。

最终至少形成一条已确认问题、一条待调查和一条被驳回意见。合格指摘必须能说明触发方式和验证方法；“建议优化性能”“可以增加注释”这类无证据泛化意见不能直接进入正式 Review。

## 9. 新人核对卡

Review 的对象是需求与代码差异，不是让 AI 对整个仓库泛泛打分。每条有效指摘包含位置、触发条件、影响、证据、修正建议和验证方法；严重度由业务后果决定，不由措辞决定。

AI 擅长扩大检查范围，却会误报或遗漏。确认顺序是：回到规格、跟踪真实调用链、构造最小复现、运行测试、再决定接受或驳回。修复指摘后还需验证没有引入回归。
