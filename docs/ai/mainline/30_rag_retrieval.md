# 第 30 章 RAG 检索

> 本章成果：构造查询、执行权限过滤和 Top-K 检索，并返回可供独立评价的来源。

检索接口输入问题和当前用户身份，输出候选 Chunk、分数及来源。可选的查询改写只能改善表达，不得改变用户身份、部门或扩大权限。

## 1. 查询处理

保留原问题，必要时抽取关键词、标准化缩写或生成检索查询。工单号、错误码等精确标识不要被意译。改写结果作为候选，并记录原查询和最终查询便于评价。

## 2. 权限过滤的顺序

身份从认证上下文获取，先构造允许的部门、角色和版本条件，再执行检索。不能把无权内容取回后交给模型过滤，因为内容已经越过权限边界。

## 3. 候选、重排和 Context

第一阶段召回候选，必要时重排；然后去重、保持段落顺序、限制总 Token，并为每块分配不可伪造的引用 ID。分数用于排序诊断，不直接当作回答置信度。

Context 构造时去除重复、控制总长度、保留来源标签，并把文档内容标记为不可信数据。若文档写着“忽略规则”，它仍是知识内容，不是系统指令。

## 4. 空结果与异常

无结果、过滤后无权限、索引不可用和查询超时是不同状态。无足够依据时应拒答或转人工，不能把低相关片段硬塞给模型生成答案。

## 5. 查询处理不是随意改写用户问题

用户问题可能包含简称、错别字、产品版本和工单编号。可以提取过滤条件、补充受控同义词或生成检索查询，但要保留原始问题。改写不能擅自改变否定、时间和对象，例如“哪些用户不能重置密码”不能改成“如何重置密码”。

## 6. 检索流水线

1. 校验用户身份和可访问范围；
2. 从问题提取部门、产品、版本等过滤条件；
3. 生成查询向量并召回候选；
4. 与关键词结果合并或重排；
5. 去重并选择满足 Context 预算的片段；
6. 保存查询、过滤、候选和最终入选结果用于调查。

权限条件必须进入数据库或检索引擎查询，不能先取回越权内容再让模型忽略。

## 7. Context 怎样构造

每个片段用稳定编号包裹，并附标题、版本和原文位置。相同内容去重，优先当前有效版本；不要只按分数从高到低塞满窗口，还要保证覆盖回答问题所需的不同证据。Context 与指令分隔清楚，文档中的命令视为资料而不是系统指令。

## 8. 空结果是一种正常业务结果

检索不到足够相关的文档时，应返回“当前知识库中没有找到依据”，并给出可选的改写或转人工方式。不能为了保持对话流畅而让模型凭训练知识补答。

验收时逐条保存 Top-K、过滤条件、最终 Context 和人工相关性标签。若答案错误但正确片段没有入选，应修检索；正确片段已入选却回答错误，才主要调查生成阶段。

没有达到门槛的结果应返回证据不足；数据库超时和真正无结果要区分。查询改写、向量生成和检索分别设置超时及日志，避免统一返回“AI 出错”而无法定位。

实践：对固定问题集比较原始查询与改写查询，记录 Recall@K、权限拒绝和耗时。验收要求：先直接检查检索结果，再进入回答生成。
