# 第 50 章 项目 Review

> 最终成果：对 ServiceDesk AI 完成架构、代码、Prompt、RAG、Agent、成本、安全、部署和交付总验收。

## 1. Review 清单

| 领域 | 必查问题 | 证据 |
| --- | --- | --- |
| 架构 | 模型与业务规则、数据库权限是否分离 | 数据流和信任边界图 |
| 代码 | 超时、错误、校验、事务和测试是否完整 | 差异与测试结果 |
| Prompt | 目标、依据、拒答和版本是否明确 | Prompt 版本与评估差异 |
| RAG | 检索和生成是否分层评价，引用能否定位 | Recall@K、支持率 |
| Agent | 工具是否最小权限，写入是否确认和幂等 | 攻击与重复调用测试 |
| 安全 | 注入、越权、数据和 Key 是否受控 | 威胁模型与安全测试 |
| 成本 | Token、请求量、缓存和预算是否可见 | 成本报告和告警演练 |
| 运维 | 日志、健康检查、发布和回滚是否可执行 | 部署及恢复记录 |

## 2. 验收过程

冻结提交和配置版本；从干净环境按 README 重建；运行普通测试、安全用例和 AI 评估；部署到隔离环境；由另一人执行核心场景和回滚。所有失败必须记录，不得把“模型偶尔如此”作为关闭缺陷的理由。

## 3. Review 的执行方式

先检查阻断交付的问题：越权、数据泄漏、错误写入、无法恢复和核心功能失败。再检查质量、成本、性能与维护性。每条指摘包含位置、触发条件、影响、证据、建议、负责人和状态；无法证明的内容列为调查项。

## 4. 端到端验收场景

至少执行：从邮件提取并人工确认；依据有权限手册回答并打开引用；无答案时拒答；Agent 查询后经确认更新；无权用户访问被拒绝；模型超时降级；预算超限停止；文档回滚和应用回滚。

## 5. 发布判定

安全硬门槛必须全部通过；质量达到预先设定阈值；P95 延迟和费用在预算内；监控与值班手顺可用；未解决风险有负责人和接受记录。平均分不能抵消一条严重越权失败。

## 6. 交付物

交付源码、依赖锁、`.env.example`、架构图、接口契约、Prompt 版本、评估数据与报告、安全说明、成本估算、部署回滚手顺和已知限制。真实 Key、客户数据、生产日志及无授权文档不得进入交付包。

## 7. 独立复跑

由未参与实现的学员依据 README、配置示例和交付说明完成启动、核心流程、失败演练和回退。任何必须口头补充的关键步骤都应回写文档。

## 8. Review 结论怎样分级

| 结论 | 含义 | 示例 |
| --- | --- | --- |
| 阻止发布 | 可能导致越权、数据损坏或核心功能失败 | 用户能读取其他部门的检索结果 |
| 发布前修复 | 重要质量或运维问题 | 模型超时没有明确错误状态 |
| 后续改善 | 当前可接受但有明确改进价值 | 诊断页面缺少按模型筛选 |
| 观察项 | 需要上线数据才能判断 | 峰值并发下的真实供应商延迟 |

每条指摘包含位置、复现条件、证据、影响、建议和确认方法。不要只写“安全性不足”或“代码需要优化”。

## 9. 从需求追溯到证据

为核心需求建立追溯表：需求编号连接设计、实现位置、测试用例和运行证据。AI 功能还要连接 Prompt、模型、Schema、评估集和索引版本。任何“已完成”都应能找到可检查证据。

## 10. 最终答辩问题

学员需要说明：为什么这里使用 LLM 而不是规则；错误输出怎样被发现；用户权限在哪些层执行；模型或索引升级怎样评价和回退；一次请求的成本怎样计算；真实故障怎样从追踪编号定位；当前系统明确不保证什么。

答辩不是背术语。评审者可临时替换一条输入、制造依赖失败或询问某条数据来源，观察学员是否能用系统行为和证据回答。

## 11. 课程完成标准

项目可由另一名学员按文档独立启动；核心流程、异常、权限和安全测试通过；评估结果达到事先定义的门槛；秘密不在代码、镜像和日志中；发布与回退演练完成；遗留风险有负责人和处理计划。满足这些条件，才表示学员具备用 AI 增强业务系统的入门工程能力。

由未参与实现的人在干净环境按交付材料复跑。记录实际版本、命令、结果和差异。若必须依赖作者口头说明才能运行，说明交付文档尚未完成。

只有当[贯穿项目规格](../project_spec.md)的功能、安全、稳定性、成本和交付条件均有实际证据时，课程主线才算完成。
