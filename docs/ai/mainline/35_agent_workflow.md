# 第 35 章 Agent Workflow

> 本章成果：实现“判断 → Tool → Result → 再判断”的受限循环，并定义停止条件。

Agent 每轮读取目标、当前状态和可用工具，选择回答、调用工具或请求人工输入。宿主程序负责执行、保存状态和限制循环。

## 1. 状态机

常见状态包括运行、等待工具、等待确认、完成、失败和取消。每次转换记录原因与结果。不要只用一个无限 `while` 循环，也不要把模型文本当作完成标志。

必须设置最大步骤、最大工具调用、总超时、预算、允许工具和重复调用检测。工具失败后可以有限重试或换方案；达到上限时返回已完成步骤、证据和阻塞原因，不无限循环。

## 2. 每轮处理

读取目标和可信状态；提供当前允许工具；解析回答或调用；校验参数和权限；执行；保存结构化结果；判断完成或继续。历史过长时只保留必要状态，业务事实重新查询。

## 3. 重试与幂等

临时只读失败可有限重试；写操作先检查是否已成功，必须带幂等键和预期版本。相同调用反复出现时停止并报告循环。

## 4. 可观测性

每一轮记录状态变化、模型与 Prompt 版本、建议动作、工具结果、耗时、Token 和停止原因，并对正文脱敏。最终状态要明确区分完成、失败、等待人工和取消。

## 5. 状态机比聊天记录更可靠

聊天文本适合表达，但不适合判断业务是否完成。Agent 状态应包含任务编号、当前步骤、已验证事实、待确认项、已执行工具、预算和最终状态。状态转换由程序验证，例如只能从 `WAITING_APPROVAL` 进入 `EXECUTING` 或 `CANCELLED`。

## 6. 每一轮发生什么

一次循环通常是：读取受控状态；构造允许的工具与指令；模型选择回答或工具；程序验证调用；执行工具；记录结果；更新状态；判断继续、等待确认、完成或失败。每轮都要减少剩余任务或增加新证据，否则可能陷入循环。

## 7. 停止条件必须可计算

包括最大轮数、总时间、Token 或费用预算、连续相同调用次数、没有新信息的轮数和业务完成条件。达到限制后返回明确状态并保存恢复点，不能用“请尽快完成”这种自然语言代替程序控制。

## 8. 重试与恢复

读取工具可按策略重试；写工具需要幂等键和执行记录。进程中断后，从持久化状态判断哪些动作已经完成，不能把整段聊天重新交给模型猜测。人工审批后也要校验任务状态和参数没有变化。

验收时故意制造工具超时、重复返回、服务重启和审批过期，检查 Agent 不重复写入、不无限循环且能说明停在哪一步。

每一步记录 trace、模型、工具、耗时、Token、状态变化和错误类别，但对正文脱敏。最终结果必须区分已完成、未完成和等待人工。

实践：让 Agent 调查一个虚构工单，只允许查询工单和搜索知识库，最多 5 步。测试正常完成、重复调用、工具持续失败和预算耗尽。

## 9. 本章核对

学员应能从任意任务状态说明上一步证据、下一步允许动作、剩余预算和停止原因。若只能查看最终聊天文本，却无法判断工具是否执行、写操作是否重复或任务能否恢复，Workflow 还不具备工程可控性。
