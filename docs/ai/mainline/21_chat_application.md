# 第 21 章 Chat 应用开发

> 本章成果：实现有明确状态归属、历史长度和数据生命周期的对话接口。

## 1. Chat 系统需要管理什么

Chat 不只是把消息数组原样发给模型。系统必须决定：谁保存历史、哪些消息进入下一轮、如何区分用户与服务端指令、何时摘要或截断、用户如何删除会话。

服务端指令不能由前端用户覆盖。历史消息属于不可信数据；旧消息中的命令也不能获得新权限。对话状态可以由应用数据库管理，也可以使用供应商提供的会话能力，但必须明确保存位置、访问权限和删除策略。

## 2. 消息角色和状态归属

服务端规则由应用维护；用户消息是输入；助手消息是生成结果；工具结果来自程序但仍需按不可信数据处理。业务状态必须重新查询权威系统，不能从旧助手消息恢复。

## 3. 历史控制

限制单条长度、轮数、总 Token 和保留时间。截断时优先保留当前目标、必要规则和最近相关事实；摘要历史可能丢信息或引入错误，重要字段需要结构化保存或重新查询。

## 4. API 与并发

会话属于当前用户。读取、追加和删除都做授权；并发发送要定义顺序、版本或互斥，避免两次回复覆盖。用户取消只表示客户端不再需要结果，服务端是否能取消下游请求要实际实现。

## 5. 前端状态

页面至少区分加载、成功、空内容、失败、取消和重试。失败消息使用稳定业务错误，不显示 Key、内部 Prompt 或供应商堆栈。

## 验证场景

至少覆盖正常多轮、超长消息、越权会话、历史裁剪、刷新恢复、并发发送、模型超时、用户取消和删除会话。每个场景都要有可观察状态与服务端证据。

## 6. Chat 不是“把所有消息都传回去”

一个 Chat 请求至少涉及四种状态：前端正在输入的临时状态、服务端认可的会话记录、发送给模型的上下文、数据库中用于审计的原始记录。它们用途不同，不能用浏览器传来的完整历史直接替代服务端记录，否则用户可能伪造角色消息或修改旧内容。

服务端应根据会话编号重新读取有权限的历史，加入受控指令，再构造模型请求。前端只提交本次用户消息和必要的并发版本信息。

## 7. 历史怎样增长和裁剪

上下文窗口有限，历史越长，延迟和费用通常越高。常见策略包括保留最近若干轮、保留关键业务事实、对较早内容生成摘要、把长期资料放到检索系统。摘要不是原始事实，重要编号、状态和承诺要以业务数据库为准。

裁剪前要先定义不可丢失信息，例如工单编号、用户已经确认的处理范围和安全限制。不能简单按字符数从开头截断，因为可能删掉系统约束或把一轮问答切成两半。

## 8. 并发和顺序问题

用户快速发送两条消息时，第二个响应可能先回来。每条消息应有独立编号、创建时间和状态，服务端用会话版本或队列确定顺序。前端需区分“等待中、流式生成、完成、失败、已取消”，失败重试也不能重复插入用户消息。

## 9. 验收用例

除正常多轮问答外，还要验证：伪造 assistant 历史被拒绝、无权访问他人会话、长会话裁剪后关键事实仍在、两次并发发送顺序正确、刷新页面后状态可恢复、删除会话后不可继续读取。学员需用日志追踪一次消息从创建到模型响应保存的全过程。

连续询问 SD-001，再切换到 SD-002，检查指代是否正确；制造超过历史上限的会话，确认截断策略；删除会话后确认不能再读取。对话答案仍需通过工具或 RAG 获取事实。

实践：实现带 `conversation_id` 的问答接口，限制单轮输入、历史轮数和总预算，并为串话和越权各写一个测试。
