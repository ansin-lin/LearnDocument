# 第 39 章 Multi-Agent 基础

> 本章成果：理解 Coordinator 与专业 Agent 的分工，并用评价数据判断多 Agent 是否值得。

多 Agent 将任务分给不同执行者，例如调查、检索、审查；Coordinator 负责分派和汇总。它可能增加并行能力，也会增加通信损失、冲突、延迟、Token 和排错难度。

## 1. 常见模式

Coordinator 分配子任务并汇总；流水线把上一步结构化结果交给下一步；并行专家独立分析后统一裁决。模式应由任务依赖决定，不为了使用多 Agent 强行拆分。

先建立单 Agent 基线。只有职责可独立、输入输出契约明确且收益可测时再拆分。多个 Agent 不得同时写同一资源；最终结论仍需证据和统一验收。

## 2. 任务拆分

子任务必须有输入、输出 Schema、允许工具、完成条件和预算。共享信息使用只读快照或版本号；写入集中到一个执行者，避免覆盖和竞态。

## 3. 汇总与冲突

Coordinator 不应只拼接回答。它要检查重复、冲突、证据和遗漏；无法裁决时交给人工。子 Agent 的文字不是自动可信证据。

## 4. 评价

用同一任务集与单 Agent 基线比较成功率、遗漏、延迟、Token、调用次数和人工介入。不能只展示一个多角色对话看起来更完整的案例。

## 5. 多 Agent 解决的是组织问题

把一个模型称为“分析员”、另一个称为“审查员”，并不会自动提高质量。只有当任务能按不同工具、权限、上下文或并行工作清楚拆分，且汇总规则明确时，多 Agent 才可能有价值。

例如工单批量分析可以按工单并行；安全审查与文档审查需要不同规则，也可拆分。一个短摘要任务没有必要经过五个角色轮流改写。

## 6. Coordinator 的职责

Coordinator 分解任务、分配输入、限制预算、收集结构化结果、处理超时与冲突并决定最终状态。子 Agent 只拿到完成子任务所需的最小数据和工具，不共享万能权限。

## 7. 结果怎样汇总

先定义统一输出 Schema、证据字段和严重度标准。冲突时保留各自结论与依据，按规则仲裁或转人工，不能让最后一个 Agent 用流畅文字掩盖分歧。重复工作通过任务编号和幂等机制去重。

## 8. 是否值得使用的实验

用同一任务集比较单 Agent 与多 Agent 的成功率、遗漏率、总延迟、Token 成本、调用次数和人工介入率。若质量提升很小但成本和排错难度显著增加，应保留更简单的方案。

本章只作为选修。学员的重点不是堆角色，而是能解释拆分边界、权限边界、失败恢复和最终责任归属。

## 9. 本章核对

采用多 Agent 前，先用单 Agent 或固定 Workflow 建立基线。拆分后每个子任务要有独立输入、输出和完成条件，Coordinator 能识别缺失、冲突和超时。不能证明质量收益大于成本与复杂度时，应回到更简单的设计。

与单 Agent 比较任务成功、证据完整、延迟、Token、工具次数和冲突率。质量没有明显提升时，复杂架构不值得保留。

实践：让单 Agent 和“调查 + Review”双 Agent 完成同一任务，比较正确率、遗漏、耗时、费用和冲突。没有明显收益时保留简单方案。
