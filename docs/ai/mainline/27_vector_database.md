# 第 27 章 Vector DB

> 本章成果：使用 PostgreSQL + pgvector 保存文档块、向量和元数据，并进行带权限条件的相似检索。

表至少保存 `chunk_id`、`document_id`、`version`、`department`、`access_role`、`content`、`embedding_model` 和向量。主线沿用已有 SQL 课程，不重复讲建表、事务和索引基础。

## 1. 为什么使用 pgvector

pgvector 在 PostgreSQL 中保存和检索向量，使业务元数据、权限条件与向量排序可以在同一查询边界处理。它不是完整知识治理系统，文档解析、版本、评价和删除仍由应用实现。

## 2. 数据一致性

原文块、向量、模型版本和权限标签必须一一对应。导入使用批次状态：准备、处理、完成或失败；只有整批验证通过后才对查询可见。更新采用新版本构建和切换，失败时保留旧版本。

## 3. 索引与查询

小数据可以精确搜索建立正确性基线；数据增长后再评估近似索引。索引参数影响召回、速度、内存和构建时间，必须用代表性数据与 `EXPLAIN` 验证。

## 4. 权限和 SQL 安全

使用服务端可信身份构造参数化查询，在数据库检索阶段应用租户、部门和文档 ACL。禁止让模型生成任意 SQL 后直接执行，也不能先检索越权数据再在 Prompt 中过滤。

## 5. 一条向量记录需要哪些字段

除向量外，通常还需要：文档编号、Chunk 编号、原文、标题、原文位置、部门或 ACL、文档版本、Embedding 模型版本、内容哈希、创建与失效时间。向量本身无法告诉你内容来自哪里，也无法支撑更新、引用和审计。

文档表保存文档级信息，Chunk 表保存分段内容和向量。删除或更新文档时，应通过外键或明确任务同步处理旧 Chunk，避免同一文档的新旧版本同时被检索。

## 6. 精确检索和近似索引

小数据集可以直接计算距离，结果精确且便于验证；数据量增长后可使用近似最近邻索引换取速度。近似索引的参数会影响构建时间、查询速度和召回率，因此要用真实规模和评估集测量，不能只确认“创建索引成功”。

数据库查询计划仍然重要：先过滤部门后做向量排序，与先扫描全部向量的成本可能差很多。

## 7. 写入与重建流程

入库任务应记录解析版本，按内容哈希跳过未变化片段；新版本先写入待发布状态，确认数量和抽样质量后再切换。失败时能从任务编号恢复，而不是重新导入全部文档。

## 8. 权限不是 Prompt 条件

“请不要返回其他部门文档”不能代替数据库过滤。权限必须在检索查询执行前生效，并使用服务端可信身份参数。测试需包含两个部门相同关键词的文档，证明用户只能检索自己允许的结果，同时检查 SQL 使用参数绑定。

当前用户、角色和部门来自认证上下文，不来自模型参数。查询值使用绑定参数，动态排序或过滤字段使用白名单。数据库账号遵循最小权限。

检索 SQL 必须使用参数绑定。权限过滤应在数据库查询或可信服务层完成，不能先取出所有结果再让模型决定能否显示。更换 embedding 模型或维度时建立新版本索引并重新生成，不静默混用。

实践：导入三份虚构手册，验证同角色命中、跨角色无结果、旧版本不返回和事务失败回滚。使用 `EXPLAIN` 观察代表性数据，不把小样本速度当成生产结论。
