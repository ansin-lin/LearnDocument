# 第 13 章 AI 辅助测试

> 本章成果：从规格推导正常、异常、边界、组合和非功能测试，并保持需求到用例可追踪。

## 1. 测试观点

对工单提取至少覆盖：最短/最长输入、合法/非法分类、多问题、缺字段、敏感文本、超时、拒答和格式错误。对 RAG 分开测试检索是否命中正确片段，以及回答是否被片段支持。

AI 擅长扩展候选场景，但容易生成重复用例和无规格依据的预期值。每条用例应写需求编号、前置数据、操作、预期结果和证据。

## 2. 从规格推导，而不是从实现猜

先拆出输入约束、业务规则、状态变化、权限和外部失败，再为每条规则设计能证明它的用例。AI 可以补充候选，但预期必须来自已确认规格。测试当前实现“现在怎么做”与验收“应该怎么做”是两种任务。

## 3. 边界不是随便取值

边界来自字段长度、枚举、时间、分页、权限和预算规则。例如最大长度为 5000，应测试 4999、5000、5001，而不是只写“测试边界值”。

## 4. AI 应用特有测试

普通自动测试使用 Fake/Mock 固定模型响应，验证程序逻辑；真实模型评估使用固定数据集观察质量，两者不能互相替代。还要覆盖拒绝、截断、非法结构、超时、限流、费用上限、Prompt Injection 和工具越权。

## 5. 用例结构

| 字段 | 内容 |
| --- | --- |
| 需求编号 | 对应哪条规格 |
| 前置状态 | 用户、权限、数据、模型替身 |
| 输入与操作 | 可复现的请求步骤 |
| 预期 | 响应、数据库、工具调用和日志 |
| 证据 | 断言、查询结果或追踪记录 |

## 6. 去重与优先级

AI 容易生成大量文字不同但验证目标相同的用例。去重时要看“触发条件 + 业务规则 + 预期结果”，而不是只比较标题。优先执行高影响、高概率、权限相关、资金或个人信息相关以及历史上出过问题的场景。

## 7. 四类基础测试观点

| 类型 | 要回答的问题 | 工单示例 |
| --- | --- | --- |
| 正常系 | 合法输入能否得到预期结果 | 有标题和正文时成功分类 |
| 异常系 | 依赖或处理失败时系统怎样响应 | 模型超时后返回可重试错误 |
| 边界值 | 临界点前后行为是否一致 | 499、500、501 个字符 |
| 权限与安全 | 不同身份能否只做允许的操作 | 普通用户不能读取其他部门工单 |

## 8. AI 功能为什么不能只断言一句固定文本

生成式模型的措辞可能变化，因此应把测试目标拆为可稳定判断的条件。例如摘要测试可以断言：不超过 120 字、包含故障对象、没有虚构工单中不存在的编号、返回结构符合 Schema。对少量难以程序化判断的“是否清晰”，再使用人工评分规则或受控的模型评分，并保留样本抽查。

## 9. 用例生成后的核对问题

- 每条用例能追溯到哪条规格或风险？
- 前置数据是否足以让另一名学员复现？
- 预期结果是否可观察，而不是“系统正常”？
- 是否覆盖空值、重复提交、并发、超时和权限差异？
- 若模型输出变化，判断标准是否仍然成立？

本章产物应是一组能执行的测试用例，而不是 AI 罗列的“测试点”。

多个用例若只换无关文字，应合并为参数化测试。先覆盖高风险业务规则和失败行为，再扩展表达多样性。不能用大量相似成功用例掩盖没有权限、异常和边界测试。

实践：为 `POST /api/ai/tickets/extract` 设计不少于 12 个用例，合并重复项，并标出哪些使用模型替身、哪些需要真实模型评价。
