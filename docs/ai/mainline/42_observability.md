# 第 42 章 AI 应用日志

> 本章成果：通过统一 trace 关联 API、模型、检索和工具调用，并在不泄露敏感正文的前提下定位问题。

日志至少记录 `trace_id`、功能、提示版本、模型配置、耗时、Token、响应状态、错误类别、检索文档 ID、工具名和确认结果。默认不记录完整 Prompt、Response、Embedding 或密钥。

## 1. 日志、指标与 Trace

日志描述具体事件；指标观察总体趋势；Trace 串联一次请求的阶段。三者结合才能回答“哪一层慢、哪类错误增加、某次调用发生了什么”。

## 2. 阶段化追踪

一次 RAG 请求至少区分输入校验、Embedding、检索、重排、模型生成和输出校验。Agent 再记录每个工具步骤。统一 `trace_id`，但不要把供应商请求 ID 当作业务身份。

指标关注成功率、超时率、限流率、P95 延迟、Token、费用、结构校验失败、拒答率和工具错误。分布式调用可使用 Trace 关联阶段耗时，但日志、指标和 Trace 各有用途，不能互相替代。

## 3. 隐私和采样

默认记录哈希或分类摘要，不保存完整用户文本。需要调试采样时明确比例、权限、保留期和删除。日志系统自身也需访问控制和审计。

## 4. 告警与排错

告警基于持续错误率、延迟、校验失败或费用异常，并链接到处理手册。排错从追踪编号进入，按认证、检索、模型、工具和保存阶段逐步定位。

## 5. 三类可观测数据

日志记录离散事件，例如请求开始和解析失败；指标记录可聚合数值，例如成功率、P95 延迟和 Token；Trace 用同一追踪编号连接浏览器、后端、检索、模型与数据库步骤。三者组合后，才能回答“哪一步慢、哪些用户受影响、从何时开始”。

## 6. AI 请求应记录什么

记录任务类型、租户和用户的安全标识、模型与 Prompt 版本、输入输出 Token、开始与结束时间、重试次数、响应状态、工具名、检索索引版本和错误类别。Prompt 正文、工单内容和模型原始输出可能含敏感信息，默认不应完整写入普通日志。

可以保存内容哈希、长度、脱敏摘要或受限审计副本。谁能查看、保存多久和怎样删除应有明确政策。

## 7. 指标必须能行动

“总请求数”只能描述流量。更有行动价值的指标包括按功能分组的失败率、首字延迟、完整延迟、结构校验失败率、无答案率、工具拒绝率和单次成功任务成本。告警要绑定处理手册，避免每次短暂波动都惊动值班人员。

## 8. 一次排错演练

制造模型超时后，从用户请求编号找到后端 Trace，确认权限和检索已成功、外部调用耗时超过预算、有限重试发生一次、最终返回可重试错误且没有重复保存。若只能看到一条“AI error”，说明可观测性仍不够。

为错误率、P95 延迟、费用突增、校验失败和安全拒绝异常设置阈值。告警必须指向可执行手册，避免所有问题都通知同一人。

实践：注入一次模型超时和一次检索空结果，通过同一 `trace_id` 还原路径。确认前端错误不含供应商秘密，运维日志又足够定位失败层。
