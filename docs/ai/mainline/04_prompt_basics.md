# 第 4 章 Prompt 基础

> 本章成果：能够把含糊请求改写为目标、依据、边界和验收方法明确的 Prompt，并判断问题来自 Prompt、上下文还是业务系统。

## 1. Prompt 是什么

Prompt 是本次任务提供给模型的指令和输入信息。它可以包含职责、背景、任务、资料、限制、示例和输出要求。Prompt 的作用是减少歧义，不是魔法口诀，也不能让模型获得不存在的数据或权限。

下面这条请求很难验收：

```text
帮我分析一下这个工单。
```

“分析”可能表示摘要、分类、调查原因或提出解决方案。没有原文、分类规则和完成条件，模型只能猜测用户真正想要什么。

## 2. 六个组成部分

### 2.1 职责（Role）

职责说明模型应站在什么业务视角完成任务，例如“你协助客服整理工单”。它不应写成夸张身份，也不产生真实权限。“你是世界顶级专家”通常不能替代资料和验收标准。

### 2.2 背景（Context）

背景说明当前业务、已有状态和使用目的。例如结果是给客服确认，还是由程序直接解析。只提供与任务相关的背景，并注明版本和来源。

### 2.3 任务（Task）

使用可观察的动词，例如提取、分类、比较、修改或生成测试。一个 Prompt 同时包含多个独立任务时，拆成步骤或分别执行。

### 2.4 依据（Evidence）

明确允许使用哪些输入，并要求结论指向依据。没有依据时，允许模型回答“不足以判断”，而不是逼它填满结果。

### 2.5 条件与边界（Constraints）

限制包括允许范围、禁止事项、长度、枚举、安全边界和停止条件。约束应能够检查，例如“摘要不超过 120 字”比“尽量简短”更明确。

### 2.6 输出格式（Output）

人阅读时可以使用标题、表格和项目符号；程序消费时使用 Structured Output 和 Schema。要求“返回 JSON”仍可能得到字段错误，后续必须校验。

## 3. Example 什么时候有用

Example 适合说明难以用一句话表达的分类边界、特殊格式或期望风格。示例应代表真实边界，不要只提供最简单的成功案例。示例中的数据和答案也可能有错，必须审核。

```text
输入：登录后立即跳回登录页。
输出：category=ACCOUNT；missing_fields=[发生时间, 浏览器]
```

如果任务只是“将标题限制为 30 字”，通常不需要大量示例。

## 4. 从含糊请求逐步改进

### 第一步：写清结果

```text
从用户原文中生成摘要、分类建议和待确认信息。
```

### 第二步：提供依据和边界

```text
只能使用用户原文和分类表。分类只能是 ACCOUNT、REPORT、ACCESS、OTHER。
缺少的信息写入 missing_fields，不得自行补全。
```

### 第三步：规定可检查输出

```text
返回 summary、category、evidence、missing_fields。
summary 不超过 120 字；evidence 必须是原文中的短片段。
```

### 完整 Prompt

```text
职责：你协助客服整理工单，不做最终业务决定。

背景：输出会显示给客服人员确认，不会直接写入数据库。

任务：根据用户原文生成摘要、分类建议、支持分类的原文证据，以及仍需确认的信息。

分类表：
- ACCOUNT：登录、密码、账号状态
- REPORT：报表生成、导出和格式
- ACCESS：成员、角色和资源访问申请
- OTHER：以上都不匹配

规则：
- 只能使用用户原文和分类表。
- category 只能取四个允许值。
- summary 不超过 120 字。
- evidence 必须逐字来自用户原文。
- 无法判断时使用 OTHER，并说明缺失信息。

输出：返回 summary、category、evidence、missing_fields 四项。

用户原文：
昨天升级后一直进不去员工门户，重置密码也没用。
```

## 5. 怎样核对回答

先检查格式和字段，再逐条追踪事实，然后检查业务规则，最后确认是否发生实际操作。不要让同一个模型仅用“你刚才回答得对吗”完成自证。

| 检查项 | 核对动作 |
| --- | --- |
| 摘要 | 与原文逐句对照，删除新增事实 |
| 分类 | 对照允许枚举和分类定义 |
| evidence | 在原文中搜索完全对应片段 |
| missing_fields | 判断是否确实未提供 |
| 权限和写入 | 查业务服务结果与审计日志 |

## 6. 常见失败及修正

| 症状 | 可能原因 | 修正方向 |
| --- | --- | --- |
| 回答很长但没有结论 | 任务和输出不明确 | 指定字段、长度和完成条件 |
| 编造账号、日期 | 没有限定依据 | 要求仅使用资料并返回缺失项 |
| 分类每次不同 | 边界和示例不足 | 明确分类定义并建立评估集 |
| 格式正确但业务错误 | 只做 Schema 校验 | 增加业务规则和人工确认 |
| 无法知道实时状态 | 没有外部数据 | 使用授权工具或业务 API |

## 7. 练习与参考标准

将“帮我看看为什么报表不对”改成完整 Prompt。已知材料只有用户原文：“8 月月报导出后，金额列显示成日期。”

合格 Prompt 应明确任务是摘要和分类还是原因调查；若只做分类，应使用 REPORT，并把报表名称、操作时间和样例文件列为待确认项；若要求根因调查，则必须请求日志、版本和复现步骤，不能让模型直接断言是格式化代码错误。

自查：删除 Prompt 中任一组成部分再次执行，记录结果发生了什么变化。最终保留真正改善固定样例的内容，不以 Prompt 越长越好作为目标。

## 8. 新人核对卡

Role 说明模型以什么职责协助，不会赋予真实系统权限；背景说明为什么做和已有事实；任务写明本次只完成什么；条件定义不能做什么；输出格式让结果可使用；Example 展示边界和风格。六部分不是固定咒语，简单任务可以短，但关键约束不能靠模型猜。

判断 Prompt 是否改善，要在同一组样例上比较遗漏、格式错误和无依据结论，而不是只看某一次回答是否更长、更客气。
