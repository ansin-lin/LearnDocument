# 第 12 章 AI + SQL

> 本章成果：让 AI 辅助生成和分析 SQL，同时核对方言、参数化、结果、权限和执行计划。

## 1. 必须提供的上下文

说明数据库产品和版本、相关表结构、约束、索引、样例数据、目标结果及数据量。没有这些信息，AI 很容易混用方言、猜字段或产生错误连接基数。

业务代码禁止把模型生成的值拼接进 SQL。字段名、排序项等不能普通参数化的部分使用服务端白名单映射；数据值使用绑定参数。

## 2. AI 可以辅助哪些 SQL 工作

AI 可以依据明确表结构生成查询草案、解释连接和聚合、构造测试数据、阅读执行计划并提出候选优化。它不能自行确认数据库方言、数据分布、索引效果和生产权限。DDL、DML 和权限语句必须先确认影响范围、事务与恢复方式。

## 3. SQL 生成的核对顺序

先核对表名、字段和方言，再核对连接条件、`NULL` 三值逻辑、过滤、聚合、排序和分页。然后用固定数据验证结果集，最后才讨论执行计划和索引。应用参数必须绑定；允许用户选择的排序字段通过白名单映射。

```sql
SELECT id, title, status, created_at
FROM tickets
WHERE owner_id = :owner_id
  AND status IN ('OPEN', 'INVESTIGATING')
ORDER BY created_at DESC, id DESC
LIMIT :limit OFFSET :offset;
```

这是 PostgreSQL 教学查询。`:owner_id`、`:limit`、`:offset` 表示由数据库驱动绑定的参数，不应替换为字符串拼接。

## 4. 优化不能只看 SQL 外观

比较修改前后的结果集、执行计划、扫描行数和真实代表性数据。索引可能改善读取却增加写入成本，不能把“加索引”当作通用答案。

## 5. 测试数据与写操作

让 AI 生成测试数据时固定字段约束和业务组合，覆盖本人/他人、开放/关闭、相同时间和空结果。写操作只在隔离数据库执行，明确事务、提交、回滚及清理；不要把真实客户数据发给模型。

## 6. 常见错误

| 错误 | 可能后果 | 检查方法 |
| --- | --- | --- |
| 漏掉租户或部门条件 | 用户看到其他组织的数据 | 对照权限规则逐项检查 `WHERE` |
| `LEFT JOIN` 后在 `WHERE` 过滤右表 | 实际效果变成 `INNER JOIN` | 用右表无数据的记录做测试 |
| 一对多连接后直接统计 | 数量被重复放大 | 先画出表关系，再检查是否需要去重 |
| 对索引列使用函数 | 可能无法有效使用索引 | 查看执行计划并比较扫描行数 |
| 拼接用户输入 | 产生 SQL 注入风险 | 使用参数绑定，不让 AI 生成字符串拼接 |

## 7. 从业务问题到 SQL 的思考顺序

“统计每个部门本月已解决工单数”不能直接翻译成一条 SQL。应先明确：本月按哪个时区计算、`resolved_at` 为空怎样处理、已重新打开的工单算不算、部门取工单创建时还是当前归属、没有工单的部门是否也要显示。只有这些业务定义确定后，表、连接和过滤条件才有唯一方向。

建议让 AI 先输出以下中间结果，再生成 SQL：

1. 用自然语言复述统计口径；
2. 列出需要的表、字段和连接基数；
3. 标明权限条件和时间边界；
4. 给出正常、空值、重复关联和跨月四组测试数据；
5. 最后生成只读查询与参数说明。

## 8. 怎样验证 AI 生成的 SQL

验证分三层。**语义层**确认结果代表业务真正想要的含义；**安全层**确认参数化、权限过滤和写操作范围；**性能层**检查执行计划、扫描量、索引和大数据量表现。查询能运行只证明语法可能正确，不代表三层都通过。

练习时至少提交：SQL、输入参数、最小测试数据、预期结果、实际结果和执行计划摘要。涉及 `UPDATE` 或 `DELETE` 时，先用同条件 `SELECT` 确认目标行，并在事务或隔离环境中演练。

重点检查遗漏租户或用户条件、`LEFT JOIN` 被 `WHERE` 条件变相改为内连接、分页排序不稳定、`NOT IN` 遇到 `NULL`、计数查询与列表过滤不一致，以及在没有执行计划时武断增加索引。

实践：让 AI 为“按当前用户查询未关闭工单”生成 PostgreSQL SQL。人工验证用户条件、`NULL`、排序、分页和参数化；再使用固定数据核对结果。AI 不得直接连接生产数据库或执行写操作。
