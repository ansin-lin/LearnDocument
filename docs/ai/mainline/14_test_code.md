# 第 14 章 AI 生成测试代码

> 本章成果：生成可重复的单元、Mock 和 API 测试，并识别“测试实现细节”和“测试真实契约”的差别。

## 1. 测试分层

- 单元测试：业务校验、Prompt 构造和响应映射。
- 客户端测试：使用假 HTTP/SDK 响应验证超时和错误转换。
- API 测试：验证状态码、响应 Schema、认证和权限。
- 真实模型评价：使用独立评估集，不替代普通自动测试。

测试默认使用假模型，避免不稳定、费用和数据泄漏。Mock 必须贴近真实接口结构；供应商 SDK 升级后要更新契约测试。

## 2. Fake、Mock 与真实调用

Fake Client 是项目接口的简单实现，适合返回预设结果；Mock 还可验证调用次数和参数；真实调用用于少量集成与质量评估。不要 Mock 被测函数本身，也不要让所有测试依赖网络。

```python
class FakeLLMClient:
    def __init__(self, result):
        self.result = result
        self.calls = []

    async def generate(self, request):
        self.calls.append(request)
        return self.result
```

该片段说明 Fake 的职责，需放入既有项目接口中才能运行。测试可以断言业务层传入了脱敏后的请求，并按 Fake 结果完成 Schema 和业务校验。

## 3. API 测试检查什么

除状态码外，还要断言响应字段、错误结构、数据库是否变化、模型是否被调用、日志是否包含 `trace_id`。输入校验应在调用模型前失败；超时应映射为稳定的业务错误。

## 4. 防止无效测试

不要让 AI 同时生成实现和只会迎合实现的断言。预期结果先来自规格。故意破坏实现，确认测试确实失败；再恢复并通过。

## 5. 常见坏测试

| 坏做法 | 问题 | 改进 |
| --- | --- | --- |
| 只断言状态码为 200 | 错误内容也可能返回 200 | 同时检查结构和关键业务字段 |
| Mock 掉被测函数本身 | 测试只证明 Mock 按配置返回 | 只替换边界外的依赖 |
| 每次测试都调用真实模型 | 慢、贵且输出波动 | 默认使用 Fake，少量契约测试调用真实服务 |
| 用生产 API Key 跑测试 | 可能泄漏并产生不可控费用 | 使用独立测试配置和限额 |
| 不验证调用参数 | 错误 Prompt 也可能被假响应掩盖 | 断言适配层收到的输入与选项 |

## 6. 一条测试代码是怎样形成的

先从规格写出 Given-When-Then：Given 是准备的工单和假模型响应，When 是调用摘要接口，Then 是 HTTP 状态、响应 Schema、摘要长度和保存结果。之后才让 AI 生成测试代码。这样可以防止 AI 根据当前实现“猜一个能通过的测试”。

测试数据应明确表达意图，例如 `ticket_without_description` 比 `data1` 更容易维护。每个测试只验证一个主要规则；多个断言可以存在，但它们应共同说明同一行为。

## 7. Fake、Mock、契约测试的选择

- **Fake**：用简单实现模拟模型，适合业务流程和异常分支，稳定且快速。
- **Mock**：记录是否以正确参数调用依赖，适合验证交互，但过多会绑定内部实现。
- **契约测试**：确认本地适配层与真实供应商 API 仍兼容，数量少、单独运行、允许产生费用。
- **端到端测试**：从界面或 API 走完整流程，验证组件连接，但不适合穷举所有边界。

提交测试时要附运行命令和结果，并演示至少一次“故意破坏实现后测试会失败”。只有能发现缺陷的测试才有价值。

- 只断言 HTTP 200，不检查内容。
- Mock 返回结构与真实 SDK 不一致。
- 使用随机或共享数据导致结果不稳定。
- 真实 API 测试没有预算、超时和跳过条件。
- 测试日志中保存完整用户文本或 Key。

实践：为模型超时、非法结构化输出和正常提取各写一个 pytest 用例。记录一次故障注入前后结果。
