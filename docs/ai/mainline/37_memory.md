# 第 37 章 Memory

> 本章成果：区分 Conversation Memory、业务状态和长期偏好，并设计保存、读取、更新与删除规则。

对话历史帮助保持上下文；业务状态是工单、审批和任务的权威数据；长期记忆是经允许保存的用户偏好或摘要。三者不能混为模型“记住了”。业务真相必须从系统记录读取。

## 1. Memory 的类别

短期历史服务当前会话；结构化状态记录任务步骤和确认；长期偏好跨会话使用；知识库保存组织资料。它们有不同的权威性、权限和保留期。

保存前确定目的、字段、保留期、访问者、更新来源和删除方式。模型总结的记忆可能错误，重要字段需要用户确认。不要保存密码、密钥和无必要的敏感对话。

## 2. 读取和更新

只读取当前任务需要且用户有权访问的记忆。新信息与旧记忆冲突时标记版本或请求确认，不让模型静默覆盖。业务状态由业务系统更新，不从对话摘要反推。

## 3. 摘要记忆风险

摘要会丢失条件、否定和时间范围。保存原始来源 ID、摘要版本和确认状态；高影响事实使用结构化字段。不要无限累积历史进入上下文。

## 4. 删除与合规

用户应能查看、更正和删除可识别的长期记忆。删除范围要覆盖主存储、索引、缓存和派生摘要，并按政策记录操作而不再次保存被删除内容。

## 5. 四种信息不要混为“记忆”

| 类型 | 示例 | 可靠来源 |
| --- | --- | --- |
| 当前会话历史 | 用户刚刚补充的错误信息 | 会话存储 |
| 用户偏好 | 默认使用日语回答 | 经用户确认的偏好库 |
| 业务状态 | 工单已关闭 | 业务数据库 |
| 检索知识 | 故障处理手册 | 有版本的知识库 |

业务状态不能由对话摘要决定。即使摘要写着“工单已关闭”，执行前仍要查询数据库当前状态。

## 6. 什么值得长期保存

只有对未来任务稳定有用、用户允许保存且有明确来源的信息才适合长期记忆。一次性的情绪、模型推测和敏感原文不应自动保存。保存前要定义用途、有效期和删除方法。

## 7. 摘要不是事实压缩算法

模型摘要可能遗漏否定、数值和未解决问题。可把摘要用于减少上下文，但关键事实应以结构化字段单独保存，并保留来源消息编号。更新时避免新摘要把旧错误不断继承。

## 8. 读取和写入都要授权

读取记忆前确认用户和任务范围；写入时记录谁触发、写了什么、来源是什么；用户应能查看、更正和删除。多租户系统需要从存储查询层隔离，不能只在 Prompt 中写“不要使用其他用户的记忆”。

验收需覆盖偏好更新、相互矛盾信息、过期信息、用户删除、跨用户隔离和会话摘要遗漏关键事实等场景。

## 9. 本章核对

每条记忆都应回答：谁提供、是否确认、用于什么、保存多久、从哪里读取、怎样纠正和删除。无法回答这些问题的信息不应自动进入长期记忆。涉及当前工单状态时，永远以有权限的业务查询结果为准。

删除要覆盖主记录、派生摘要、向量和缓存，并区分依法必须保留的审计记录。备份中的处理遵循组织政策，不能承诺无法实现的立即彻底删除。

实践：为 ServiceDesk AI 设计数据生命周期表，并验证用户删除会话后，缓存、历史和派生摘要是否按策略处理。
