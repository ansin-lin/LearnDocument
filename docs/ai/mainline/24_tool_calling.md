# 第 24 章 Function / Tool Calling

> 本章成果：让模型选择只读工具，同时由程序校验参数、权限并执行。

模型看到的是工具名称、用途和参数 Schema，它返回调用建议；真正的函数由应用执行。模型没有因为“选择了工具”就获得数据库权限。

## 1. 工具定义

名称要稳定，描述写清何时使用、输入、输出、副作用和错误。参数 Schema 只暴露必要字段。当前任务不需要的工具不要提供；模型能看到工具不代表用户有权执行。

一个完整循环是：发送工具定义和问题；读取工具调用；验证工具名和参数；以当前登录用户做授权；执行；把结构化结果返回模型；获取最终回答。工具失败也要返回明确、最小的信息。

## 2. 服务端校验

依次校验工具是否允许、参数 Schema、业务值、当前身份权限、资源归属和调用预算。写工具还需人工确认、幂等键、预期版本和事务。不要让模型生成 SQL、URL 或文件路径后直接执行。

## 3. 并行、重试与停止

只有互相独立且无副作用的调用才考虑并行。重试前判断工具是否幂等；达到工具次数、总步骤、超时或预算上限时停止并报告未完成事项。

## 4. 工具结果仍不可信

远端 API、网页、数据库备注和文件都可能包含错误或注入文字。保留来源和状态，只把结果当作数据；模型对结果的解释还需经过业务验证。

## 5. 一次 Tool Calling 的真实流程

模型不会替应用直接执行数据库或 API。流程是：应用把可用工具的名称、说明和参数 Schema 发给模型；模型返回“建议调用哪个工具以及参数”；应用验证身份、权限、参数和业务状态；应用执行工具；再把结果发回模型，由模型继续判断或组织回复。

因此，模型是“提出调用计划的一方”，程序才是“授权并执行的一方”。

## 6. 工具说明怎样影响选择

工具名要具体，例如 `get_ticket_by_id` 比 `query_data` 清楚。说明要写清用途、不适用情况和副作用；参数要用严格 Schema 限制类型、长度和枚举。两个工具职责重叠时，模型更容易选错。

查询工具与修改工具应分开。`update_ticket_status` 要求工单编号、目标状态和变更理由，服务端仍需检查当前状态是否允许转换。

## 7. 高风险操作需要确认

发送邮件、修改状态、删除数据和产生费用的工具，不能因为模型给了参数就立即执行。应展示将要执行的动作，让有权限的用户确认，或进入现有审批流程。确认内容应绑定工具名、参数和有效期，防止确认后参数被替换。

## 8. 循环、幂等与结果大小

Agent 可能重复调用同一工具。通过最大轮数、重复调用检测和停止条件限制循环；写工具使用幂等键防止重复副作用。工具返回的数据只包含模型完成任务所需字段，过大的数据库结果应分页、过滤或摘要。

验收至少包括：正确选工具、错误参数被拒绝、越权被拒绝、用户取消写操作、工具超时、重复调用不产生重复修改、恶意工具结果不能改变系统规则。

远端 API、网页和文档可能返回注入文本或错误数据。将结果作为数据提供，保留来源与状态；最终回答要区分工具事实和模型解释。

只暴露当前任务需要的工具，描述副作用、错误和使用条件。首先实现 `get_ticket(ticket_id)`，禁止使用任意 SQL 工具。参考[官方 Function Calling 指南](https://developers.openai.com/api/docs/guides/function-calling)。

实践：验证本人工单、他人工单、非法编号、工具超时和模型未调用工具五种情况。审计日志记录调用者、工具、参数摘要和结果，不记录秘密。
