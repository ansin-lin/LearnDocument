# 第 32 章 RAG 准确度改善

> 本章成果：通过受控实验调整 Chunk Size、Top-K、Metadata 和检索策略，并用同一评估集比较。

一次只改变一个主要变量。先保存基线的检索命中率、回答支持率、无依据回答率、延迟和费用，再调整切分、K、过滤或排序。开发样例用于调参，独立评估集用于确认泛化效果。

## 1. 先定位失败层

解析错误先修文档处理；正确块未进入候选再调检索；候选正确但回答错误再调 Prompt 或模型；来源过期则修知识治理。未定位就同时改 Chunk、K 和 Prompt，无法知道改善来自哪里。

更大的 K 可能提高召回，也可能增加噪声、Token 和延迟；更小 Chunk 定位精确但可能丢失上下文。结论必须绑定当前文档与问题集。

## 2. 可调整变量

包括结构化切分、重叠、查询改写、关键词/向量混合、元数据过滤、Top-K、阈值、重排和上下文模板。每个变量写出假设、预期改善和可能代价。

## 3. 指标组合

同时看 Recall@K、Precision@K、引用正确率、声明支持率、适当拒答率、延迟和 Token。只提升最终回答评分可能掩盖越权或引用错误。

## 4. 实验记录

记录假设、评估集、索引快照、修改变量、指标、退化样本和结论。没有固定基线或同时改动多项参数，就无法判断改善来自哪里。

## 5. 不要一开始就调 Prompt

当答案错误时，先查看解析文本是否正确，再看正确 Chunk 是否存在、是否被召回、是否进入最终 Context，最后才检查生成指令。若正确资料根本没进入 Context，反复改 Prompt 通常无效。

## 6. 常见变量及其影响

| 变量 | 调大或改变可能带来的好处 | 风险 |
| --- | --- | --- |
| Chunk 大小 | 保留更完整上下文 | 混入多个主题，定位不准 |
| Chunk 重叠 | 减少边界信息丢失 | 重复候选和成本增加 |
| Top-K | 提高找到资料的机会 | 噪声增多、Context 变长 |
| Metadata 过滤 | 缩小范围、保证版本与权限 | 条件错误会漏召回 |
| Query 改写 | 处理简称与口语表达 | 改变原意或否定关系 |
| Rerank | 改善候选顺序 | 增加延迟和费用 |

## 7. 建立可比较的实验

固定评估集、索引快照、模型版本和评分规则，每次只改变少量变量。记录实验假设，例如“按标题边界切块能提高跨段说明的 Recall@5”，而不是只写“尝试 Chunk 500”。

报告至少包含检索召回、引用正确率、答案忠实性、无答案正确率、延迟和成本。只提升平均分但让权限场景退化的方案不能上线。

## 8. 错误分析比总分更重要

把失败分为解析、切块、过滤、召回、排序、Context 组装、生成和资料本身错误。每类选代表样本人工检查。最终应能说明“改了什么、为什么改、哪些样本改善、哪些退化、是否接受权衡”，而不是只说“效果更好了”。

固定代码、文档版本、评估集和其他参数；保存基线与候选配置；报告总体和失败类别。对关键安全用例设置不可退化门槛。

实践：至少完成三组对照实验，写明假设、变量、固定条件、结果和结论。没有改善时保留结果，不选择性删除失败实验。
