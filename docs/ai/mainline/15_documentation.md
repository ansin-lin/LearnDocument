# 第 15 章 AI 辅助文档

> 本章成果：用 AI 起草设计和接口说明，并通过代码、配置和测试证据保持文档一致。

AI 可以整理现状、生成表格和发现术语不一致，但不能凭接口名推断实现。基本设计描述外部契约、业务流程和异常；详细设计描述实际模块、方法、数据传递和处理顺序；接口设计应与 OpenAPI 和测试响应一致。

## 1. 不同文档回答不同问题

| 文档 | 主要读者 | 重点内容 |
| --- | --- | --- |
| 基本设计 | 业务、测试、开发 | 外部行为、流程、权限、异常 |
| 详细设计 | 开发与维护者 | 模块、函数、数据传递、算法 |
| 接口设计 | 前后端与调用方 | 请求响应、状态码、认证、示例 |
| 代码说明 | 维护者 | 难理解的原因、边界和约束 |

不要让 AI 把所有内容复制到每份文档。文档只写当前读者需要且能够维护的信息。

## 2. 给 AI 的材料

提供当前规格、实际代码、配置、接口 Schema、测试和目标文档模板，明确哪个是权威来源。若设计与实现冲突，先输出差异，不擅自把一方覆盖成“最新”。

## 3. 文档核对

逐项对照路由、请求字段、类型、必填性、枚举、响应、错误码、认证、超时和副作用。凡是写“已验证”的内容必须附实际命令或结果；未来方案标为计划，不伪装成现状。

## 4. 变更影响

接口字段改变时，同时检查 OpenAPI、示例请求、前端类型、测试、错误表和交付说明。Prompt、模型和 RAG 配置也应版本化，但不要在公开文档中写真实 Key 或内部敏感内容。

## 5. 常见问题

AI 容易生成不存在的类名、把推测写成现状、遗漏异常分支、复制旧字段和使用空泛句子。发现冲突时先列出证据与待确认项，不要自动把某一份材料当作最新版。

## 6. 文档不是同一种粒度

| 文档 | 主要读者 | 必须回答的问题 |
| --- | --- | --- |
| 基本设计 | 业务、测试、开发 | 系统要提供什么功能和外部行为 |
| 详细设计 | 开发与维护人员 | 模块、数据和异常怎样实现 |
| API 设计 | 前后端与调用方 | 请求、响应、认证、错误和版本是什么 |
| 运维手册 | 值班与发布人员 | 怎样部署、监控、回退和调查 |
| 代码说明 | 后续修改者 | 为什么这样实现，有哪些约束 |

让 AI 写文档前，必须指定文档类型和读者。否则它可能把代码级细节塞进基本设计，也可能只写宣传式概述。

## 7. 从证据生成，而不是凭空补全

AI 可以根据规格、代码差异、接口 Schema、数据库定义和测试结果生成初稿。材料中没有的信息应标记为“待确认”，不能让模型自行补上。例如代码没有超时值时，文档不应写“超时为 30 秒”。

建议把每个结论标记来源：`规格`、`代码`、`配置`、`测试证据` 或 `人工决定`。审阅者可以快速判断内容是否有依据。

## 8. 文档完成后的核对

按“名称一致、字段一致、流程一致、异常一致、权限一致、版本一致”检查。再请一名不了解实现的人按文档完成一次调用或操作；如果他必须猜参数、错误处理或开始状态，文档还没有达到可交接程度。

本章练习要求用同一项工单摘要功能生成 API 说明和运维排错说明，并解释为什么两份文档的读者、内容和粒度不同。

AI 容易生成不存在的类名、把推测写成现状、遗漏异常分支、复制旧字段和使用空泛句子。每段说明都应能帮助实现、验证或排错，否则应删除。

实践：给 AI 一份过期接口说明和当前代码，让它生成差异表。人工核对后只更新有证据的项目，并保留待确认项。
