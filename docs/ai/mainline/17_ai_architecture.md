# 第 17 章 AI 开发整体架构

本章不重新教授 React 或 FastAPI 语法，而是说明它们接入 LLM 后新增了哪些职责。目标是画出一张能指导开发、测试和排错的架构图。

> 本章成果：画出 React、FastAPI、LLM API、数据库和知识库的数据流，并标明信任边界与失败路径。

## 1. 总体结构

```text
React 浏览器
  │ HTTPS：用户输入、确认、取消
  ▼
FastAPI 业务 API
  ├─ 认证与授权
  ├─ 输入/输出与业务校验
  ├─ AI Service ──模型 API
  ├─ Tool Service ──业务数据库/API
  └─ Retrieval Service ──pgvector/文档
```

API Key 只在后端。模型不能直接连接数据库；它返回文本、结构化结果或工具调用建议，由服务端校验。React 负责交互状态，不承担秘密保存或最终授权。

## 2. 各层职责

React 收集输入、显示加载/流式/失败状态和人工确认；FastAPI 负责认证、校验、业务流程和错误契约；AI Service 隔离供应商接口；Tool Service 执行受控业务能力；Retrieval Service 负责文档权限与检索；数据库保存权威业务状态。

## 3. 三条数据流

普通生成只经过 AI Service；RAG 先检索再生成；Tool Calling 由模型提出调用、服务端验证执行、结果返回模型。三条路径共享认证、日志、超时和预算，但不能把检索或写权限交给模型决定。

## 4. 同步、异步与后台任务

短请求可同步等待；Streaming 用事件持续返回；耗时文档处理应创建任务并查询状态。`async def` 不会自动让阻塞 SDK 或 CPU 解析变快，必须确认依赖是否支持异步或移到合适执行器。

## 5. 失败设计

为认证失败、模型超时、限流、格式错误、检索无结果、工具失败和数据库保存冲突分别定义责任层、对外错误和可重试性。失败不能统一吞成“AI 出错”。

## 6. 一次请求怎样穿过系统

以“生成工单摘要”为例：浏览器提交工单编号；后端校验登录身份和工单权限；业务层读取工单正文；AI 适配层构造指令并调用模型；返回值先通过结构和业务校验；数据库保存摘要、模型版本与追踪编号；最后 API 返回结果。任何一步失败，都应有明确的错误归属和对用户可理解的响应。

不要让浏览器直接调用模型供应商。否则 API Key 会暴露，权限规则容易绕过，Prompt 和模型版本无法统一，成本与日志也难以治理。

## 7. 各种数据为什么不能混在一起

- **业务数据**由数据库管理，例如工单、用户和审批状态。
- **会话状态**描述本次交互，例如消息历史和当前任务编号。
- **模型配置**描述怎样调用模型，例如模型能力、超时和输出 Schema。
- **审计数据**记录谁在何时请求了什么以及系统做了什么。

模型输出只能成为“候选业务数据”。在保存前还要经过结构校验、权限检查和业务规则校验。

## 8. 架构核对清单

学员应能在图上指出：信任边界在哪里、API Key 位于哪里、用户权限在哪一层执行、超时和重试由谁负责、模型不可用时怎样降级、每次调用怎样追踪、费用怎样归属。如果这些问题没有明确答案，系统还只是“能调用模型的演示”，不是可运营的业务应用。

分别定义输入非法、模型超时/限流、结构校验失败、检索为空、工具拒绝、数据库失败和用户取消。对外错误保持稳定，内部日志保存可追踪原因，不能把供应商原始错误和秘密直接返回。

为每条外部调用画出成功、超时、限流、拒绝、非法响应和取消路径。确定性业务规则仍由普通代码执行。

实践：为贯穿项目补充组件责任表和数据分类，标出哪些内容会离开组织边界。验收要求：任何写入都能找到认证、授权、确认和审计位置。
