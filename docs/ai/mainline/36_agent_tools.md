# 第 36 章 Agent Tools

> 本章成果：为数据库、API、文件和搜索能力设计最小工具，并按副作用分级授权。

工具描述要写清用途、适用条件、参数、返回值、副作用、是否可重试和常见错误。不要暴露“执行任意 SQL”“读取任意文件”或“请求任意 URL”这类宽泛工具。

## 1. 工具契约

工具输入使用严格 Schema，返回稳定状态、数据和错误类型。描述要让模型知道何时用、何时不用，并说明结果字段。工具内部仍进行普通认证、授权和业务校验。

建议分级：只读查询可自动执行但仍需授权；可逆写操作需要确认和幂等键；高风险或不可逆操作保持人工流程。文件工具限定根目录和类型，网络工具限定目标域名。

## 2. 四类工具边界

数据库工具暴露业务查询而非任意 SQL；API 工具限制域名、方法和超时；文件工具校验绝对路径落在允许根目录；搜索工具保留来源并防止返回内容成为指令。

## 3. 错误和副作用

区分参数非法、无权限、不存在、冲突、超时和暂时失败。写工具返回资源版本和幂等结果，便于 Agent 判断是否已经完成，避免重复执行。

## 4. 工具选择评价

用固定任务统计正确工具选择、参数有效率、无效调用、平均轮数和副作用错误。安全类失败不能被较高的平均任务成功率抵消。

## 5. 工具是一份程序契约

契约包括名称、用途、输入 Schema、输出 Schema、认证来源、权限要求、副作用、超时、错误类型和幂等规则。模型看到的是工具说明，但服务端必须独立执行全部检查。

例如 `search_tickets` 是只读工具，限制查询范围和返回数量；`change_ticket_status` 是写工具，要求当前状态、目标状态、理由和幂等键，并可能需要人工确认。不要做一个万能 `execute_sql` 工具交给 Agent。

## 6. 最小权限与数据最小化

工具使用当前用户或受限服务身份，只获得完成任务需要的权限。返回结果只包含必要字段；个人信息、密钥和内部错误堆栈不交给模型。文件工具限制目录、类型和大小，URL 工具限制协议、域名和内网地址。

## 7. 错误要可供程序判断

不要只返回“执行失败”。结构化错误至少区分参数错误、无权限、未找到、冲突、限流、超时和内部错误，并标记是否可重试。模型可以据此选择补参数、询问用户或停止，但不能覆盖权限失败。

## 8. 怎样评价工具设计

用固定任务集统计正确工具选择率、参数有效率、无效调用次数、平均轮数、成功率和副作用错误数。还要测试相似工具名、含糊请求、恶意参数、超大结果和重复调用。工具选择率高但越权一次，仍然不能视为合格。

记录模型选错工具、漏调用、参数错误和不必要调用。工具越多不一定越强；只提供当前步骤所需子集通常更可控。

实践：为 `get_ticket`、`search_knowledge` 和 `update_ticket_status` 编写 Schema 与权限表。用路径穿越、越权 ID、重复请求和伪造确认测试拒绝行为。
