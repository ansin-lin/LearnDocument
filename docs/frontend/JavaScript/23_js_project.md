## 1. 完成目标

在已经完成 HTML 和 CSS 的有給休暇申請系统中，为七个页面分别实现对应的 JavaScript 行为。

```text
login.html         → js/login.js
register.html      → js/register.js
index.html         → js/index.js
apply.html         → js/apply.js
confirm.html       → js/confirm.js
complete.html      → js/complete.js
applications.html  → js/applications.js
```

完成后应能够演示：

1. 使用固定研修账号完成模拟登录；
2. 验证注册画面的输入，但不保存账号和密码；
3. 显示当前研修员工资料和申请汇总；
4. 输入休假申请并进入确认页；
5. 修正或正式提交申请；
6. 显示受付番号；
7. 筛选和取消申请；
8. 退出后清理会话数据；
9. 刷新页面后仍能读取已提交申请。

> 本练习不实现 Web Crypto、真实注册和真实身份认证。不得把密码保存到浏览器存储。

## 4. 脚本组织规则

### 4.1 页面与脚本一一对应

每个页面只加载自己的脚本：

```html
<script src="js/apply.js" defer></script>
```

`apply.js` 只处理申请输入画面，不查询申请一览画面的元素，也不执行登录页初始化。

这样可以从文件名判断修改范围：

| 修改内容 | 主要调查文件 |
| --- | --- |
| 登录校验 | `login.html`、`js/login.js` |
| 注册输入校验 | `register.html`、`js/register.js` |
| 首页汇总 | `index.html`、`js/index.js` |
| 申请输入 | `apply.html`、`js/apply.js` |
| 确认和提交 | `confirm.html`、`js/confirm.js` |
| 完成结果 | `complete.html`、`js/complete.js` |
| 一览、筛选和取消 | `applications.html`、`js/applications.js` |

### 4.2 函数职责

页面脚本内部仍要拆分函数。以 `applications.js` 为例，可以划分为：

```text
readApplications
filterApplications
renderApplications
cancelApplication
showMessage
initialize
```

函数名称应表达处理目的。不要把读取、筛选、DOM 创建、保存和消息显示全部写在一个事件监听器中。

### 4.3 重复代码的处理

本练习优先检查页面职责和基础 JavaScript，不要求额外建立公共模块。

多个页面都需要的短小处理可以暂时分别实现，但以下内容必须保持一致：

- 存储键；
- 字段名；
- 状态值；
- 部门、休假类型和状态显示文字；
- 无登录、读取失败和保存失败时的处理原则。

完成基础验收后，可以把稳定的共通函数整理为模块，但不得因此改变七个页面与七个入口脚本的对应关系。

## 5. 分阶段实施

### 5.1 第一阶段：连接脚本

为七个页面分别加载对应脚本。

每个脚本先输出仅用于连接确认的消息：

```js
console.log("apply.js loaded");
```

依次打开七个页面，确认：

- 对应脚本能够加载；
- Network 中没有 404；
- Console 没有语法错误；
- 不会加载其他页面的入口脚本。

确认完成后删除临时日志。

### 5.2 第二阶段：模拟登录和注册校验

先完成：

- `login.js`：固定研修账号判定、会话保存和跳转；
- `register.js`：账号、密码确认、姓名和所属校验。

注册页不保存用户和密码。登录页只保存固定研修用户对象，不保存输入密码。

### 5.3 第三阶段：登录状态和退出

在五个业务页面分别实现登录状态检查。

检查结果：

- 已登录：继续初始化；
- 未登录：跳转登录页；
- JSON 损坏：清理无效会话后跳转。

在 `index.js` 中实现退出，清除当前用户、草稿和最后受付番号，但保留申请记录。

### 5.4 第四阶段：申请输入

在 `apply.js` 中完成：

1. 取得表单值；
2. 校验必填、日期范围和业务条件；
3. 计算申请日数；
4. 创建草稿对象；
5. 保存到 `sessionStorage`；
6. 跳转确认页；
7. 从确认页返回时恢复草稿。

### 5.5 第五阶段：确认和提交

在 `confirm.js` 中完成：

1. 读取并验证草稿；
2. 使用 `textContent` 显示确认内容；
3. 生成 `REQ-YYYYMMDD-NNN`；
4. 保存正式申请；
5. 保存最后受付番号；
6. 仅在全部保存成功后删除草稿；
7. 跳转完成页；
8. 防止连续点击产生重复数据。

### 5.6 第六阶段：完成画面

在 `complete.js` 中读取最后受付番号并显示。

本画面不自动跳转。使用者确认编号后，自行选择返回首页或打开申请一览。

### 5.7 第七阶段：首页与一览

在 `index.js` 中计算：

- 有給残日数；
- 申請中件数；
- 当月承認済日数。

在 `applications.js` 中实现：

- 列表渲染；
- 状态筛选；
- 受付番号或理由检索；
- 条件清除；
- `pending` 申请取消；
- 空数据和读取失败状态。

## 6. 数据更新顺序

提交申请时，顺序必须保持一致：

```text
再次确认草稿
      ↓
读取现有申请
      ↓
生成受付番号
      ↓
创建正式申请
      ↓
保存申请数组
      ↓
保存最后受付番号
      ↓
删除草稿
      ↓
跳转完成页
```

如果保存申请数组失败：

- 不显示成功；
- 不删除草稿；
- 不跳转完成页；
- 恢复提交按钮；
- 显示可理解的错误。

取消申请时也要先确认记录仍然存在、属于当前员工且状态仍为 `pending`，然后再更新和保存。

## 7. 页面状态

每个动态页面至少处理与自身相关的状态：

| 状态 | 页面表现 |
| --- | --- |
| 初始 | 固定页面结构正常显示 |
| 输入错误 | 字段附近显示错误并聚焦第一个错误 |
| 处理中 | 提交按钮暂时禁用 |
| 成功 | 显示成功结果或进入下一画面 |
| 空数据 | 显示明确的无数据文字 |
| 读取失败 | 显示错误，不伪装成空数据 |
| 保存失败 | 保留可恢复数据，不继续跳转 |
| 未登录 | 返回登录画面 |

不要只在 Console 输出错误。Console 用于开发者排错，页面消息用于告知使用者当前结果。

## 8. 完成判定

提交前应完成正式任务中的 JS-01～JS-18，并重点确认：

- 七个 HTML 文件分别加载正确的七个脚本；
- 密码没有进入任何浏览器存储；
- 未登录不能停留在业务页面；
- 草稿可以进入确认页并返回修改；
- 连续点击只生成一条申请；
- 完成页刷新不会新增申请；
- 申请筛选条件可以组合；
- 取消只更新状态，不删除记录；
- 无效 JSON 不会被静默覆盖；
- 用户输入不会被当作 HTML 执行；
- 退出清除会话数据但保留申请；
- Console 没有未处理错误。
