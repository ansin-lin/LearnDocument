# 第 23 章 SES 改修与影响范围调查

真实项目中的常见任务不是从零创建系统，而是在既有代码和规格约束下完成小范围改修。本章继续使用第 22 章完成的 Vue 版“有給休暇申請システム”，实施与原 JavaScript 综合练习相同的改修：为申请一览增加申请期间筛选。

## 本章目标与任务边界

- 【必须掌握】先确认规格和影响范围，再修改代码。
- 【必须掌握】正确实现日期筛选，并保持原有筛选功能不受影响。
- 【必须掌握】通过功能确认、Review 指摘修正和 Regression Test 完成交付。
- 【会使用、能看懂】在信息不完整时整理确认事项，不擅自扩大规格。

开始状态为第 22 章已通过验收的 Vue 项目。不得借本次小改修更换状态管理方式、重写页面、修改存储结构或升级无关依赖。

## 1. 改修规格

> 申請一覧画面に「開始日」と「終了日」の検索条件を追加してください。両方が入力された場合は、指定期間と重なる申請を表示してください。既存の状態検索とキーワード検索はそのまま利用できること。

具体要求：

- 开始日和结束日具有明确标签；
- 两个日期都未输入时，结果与改修前一致；
- 只输入开始日时，显示申请结束日不早于该日的记录；
- 只输入结束日时，显示申请开始日不晚于该日的记录；
- 两者都输入时，显示与指定期间有重叠的申请；
- 结束日早于开始日时显示输入错误，不执行筛选；
- 日期条件与原有状态、关键字条件同时生效；
- 清除操作恢复全部筛选条件；
- 不在前端自行修改申请数组，筛选条件交给既有 API。

## 2. 规格确认

修改前确认并记录：

| 确认项 | 需要明确的内容 |
| --- | --- |
| 日期边界 | 与条件同一天开始或结束是否算重叠 |
| 空条件 | 未输入的一侧是否表示无限制 |
| 无效范围 | 阻止筛选还是自动交换日期 |
| 条件保存 | 页面刷新后是否需要保留条件 |
| 时区 | 当前字段是 `YYYY-MM-DD`，是否按日期字符串比较 |

本任务按“包含边界、空的一侧表示无限制、日期逆转时阻止筛选、刷新后不要求保存条件”实施。项目规格另有说明时，以项目规格为准。

## 3. 影响范围调查

沿着数据流调查，而不是只搜索页面文字：

```text
日期输入
        ↓
页面中的筛选条件
        ↓
日期范围校验
        ↓
查询条件的传递
        ↓
API Query 参数
        ↓
后台筛选结果
        ↓
申请一览显示
        ↓
功能确认与改修记录
```

调查时至少确认：

| 调查对象 | 需要确认的内容 | 验证方法 |
| --- | --- | --- |
| 筛选输入 | 当前状态、关键字和清除操作如何工作 | 页面操作 |
| 查询条件 | 条件如何从页面传递到请求 | 浏览器 Network 面板 |
| API 契约 | 日期参数的名称、格式和空值处理 | API 规格与请求内容 |
| 一览显示 | 加载中、无结果、失败和正常结果如何显示 | 页面操作 |
| 响应式布局 | 增加输入项后是否发生溢出 | 360px 宽度检查 |
| 原有功能 | 状态、关键字、取消等功能是否受到影响 | Regression Test |

实际修改范围由调查结果决定。已经能够接收并传递任意查询参数的处理不需要为了本任务重复修改，也不要为了配合示例名称拆分或新建文件。

## 4. 修改设计

页面可以增加以下局部状态：

```js
const startDate = ref('')
const endDate = ref('')
const dateError = ref('')
```

后台使用的日期区间重叠判断为：

```text
申请结束日 >= 查询开始日
并且
申请开始日 <= 查询结束日
```

某一侧未输入时，前端省略对应 Query 参数。后台参考程序已经支持 `startDate` 和 `endDate`，学员不需要修改 Node.js 代码；前端负责阻止日期逆转并正确形成请求。

功能职责保持如下：

- 页面维护筛选输入、校验错误和查询时机；
- 日期条件只用于查询，不直接修改已取得的申请数据；
- 查询时只发送非空的日期条件；
- 后台负责最终的日期范围校验和数据筛选；
- 清除函数一次恢复关键字、状态、开始日、结束日和错误消息。

## 5. 实施顺序

1. 操作现有状态筛选、关键字检索和清除功能，记录改修前结果。
2. 增加开始日和结束日输入，并设置清楚的标签。
3. 增加日期逆转校验和页面错误消息。
4. 查询时把非空日期条件与状态、关键字条件一起发送。
5. 更新清除条件处理。
6. 检查加载中、无结果、读取失败和正常结果显示。
7. 检查 360px 宽度下的页面布局。
8. 执行本章功能确认和原有功能的 Regression Test。
9. 整理影响调查、改修内容和确认结果。

不要为本次改修增加不必要的全局状态，也不要在前端复制一套与后台不同的日期筛选规则。

## 6. 必须确认的功能场景

| 编号 | 测试内容 | 预期结果 |
| --- | --- | --- |
| CHG-01 | 日期条件为空 | 结果与改修前一致 |
| CHG-02 | 只输入开始日 | 显示结束日不早于该日的申请 |
| CHG-03 | 只输入结束日 | 显示开始日不晚于该日的申请 |
| CHG-04 | 输入完整期间 | 显示与指定期间重叠的申请 |
| CHG-05 | 结束日早于开始日 | 显示错误，不执行筛选 |
| CHG-06 | 日期、状态和关键字组合 | 只显示满足全部条件的申请 |
| CHG-07 | 清除条件 | 所有条件恢复默认值 |

CHG-05 中的“不执行筛选”是指不发送查询请求，并保留上一次正常查询的结果。修正日期或清除条件后，错误消息应消失。

Regression Test 还应覆盖登录、首页汇总、申请输入、确认提交、完成页刷新、原状态筛选、关键字检索和取消申请。以上项目通过实际页面操作和浏览器 Network 面板确认，不要求为本章搭建单元测试环境。

## 7. Review 与指摘修正

Review 请求中写明：

- 规格理解与日期边界；
- 调查过的输入、请求、显示和原有功能；
- 实际改修范围；
- 正常、边界和异常测试结果；
- 未修改部分及理由；
- 仍待确认的限制。

收到指摘后，先判断同一筛选逻辑是否影响空状态、清除操作、移动端布局和测试，再修改。不要只修 Reviewer 指出的单行而遗漏相同问题。
