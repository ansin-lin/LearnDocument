# 第 22 章 SES改修与影响范围调查

真实项目中的常见任务不是从零创建系统，而是在既有代码和规格约束下完成小范围改修。本章给出已完成的WorkHub，要求为任务列表增加“担当者”筛选条件，并留下完整调查、修改和验证证据。

## 本章目标与任务边界

- 【必须掌握】先确认规格和影响范围，再修改代码。
- 【必须掌握】同步处理类型、组件、URL、API、Store和测试之间的契约。
- 【必须掌握】通过自测、Review指摘修正和Regression Test完成交付。
- 【会使用、能看懂】在信息不完整时整理确认事项，而不是自行扩大规格。

开始状态为第21章已通过验收的WorkHub。不得借本次小改修无理由更换状态管理方式、重写页面或升级无关依赖。

## 1. 改修规格

任务列表的搜索区域增加“担当者”筛选：

- 下拉框显示“全部担当者”和当前可选担当者；
- 选择担当者后，只显示该担当者的任务；
- 担当者条件可以与关键字、状态同时使用；
- 条件写入URL query，刷新和复制URL后可以恢复；
- 没有符合条件的任务时显示筛选无结果提示；
- 清除条件后恢复全部任务；
- API支持时把`assignee`作为查询参数发送；不支持时必须根据规格确认前端筛选边界。

尚未明确的事项，例如担当者列表来源、离职人员显示规则、空字符串含义和URL参数名，应先记录为确认事项。

## 2. 规格确认

修改前整理以下内容：

| 确认项 | 示例结论或问题 |
| --- | --- |
| query名称 | 使用`assignee`还是`assigneeId` |
| 值的含义 | 姓名、员工编号还是账号ID |
| 选项来源 | 任务数据去重还是单独调用用户API |
| 筛选位置 | 服务器筛选还是前端已读取数据筛选 |
| 未指定值 | 省略参数还是发送空字符串 |
| 权限与数据范围 | 是否只显示当前用户可见担当者 |

不要根据页面标签“担当者”就假设后端参数一定是姓名。规格、API定义和既有实现冲突时，应提出问题并等待项目决定。

## 3. 影响范围调查

沿着数据流调查，而不是只搜索页面文字：

```text
Task类型中的assignee
        ↓
TaskSearch输入与Emit
        ↓
Router query读取、转换与更新
        ↓
TaskListView组合条件
        ↓
Pinia Action
        ↓
tasks API查询参数
        ↓
组件、Composable、Store和页面测试
        ↓
README / 规格说明
```

调查表至少记录：

| 位置 | 当前职责 | 是否修改 | 修改理由 | 验证方法 |
| --- | --- | --- | --- | --- |
| `types/task.ts` | 定义任务字段 | 通常否 | 已有`assignee` | 类型检查 |
| `TaskSearch.vue` | 输入筛选条件 | 是 | 增加选择框与事件 | 组件测试 |
| `router/index.ts`或列表页 | 管理query | 是 | URL可复现 | 刷新与前进后退 |
| `stores/tasks.ts` | 调用读取Action | 视设计 | 转交条件，不解析DOM | Store测试 |
| `api/tasks.ts` | 形成请求参数 | 是 | 对接API契约 | Mock断言 |

也要搜索`assignee`、当前筛选类型、路由query、API函数名和相关测试，确认没有遗漏直接引用。

## 4. 修改设计

在编码前写清数据契约。例如：

```ts
export interface TaskSearchCondition {
  keyword: string
  status: TaskStatus | ''
  assignee: string
}
```

若项目已存在相同职责的类型，应扩展既有类型，不要重复创建近似接口。Router query来自URL，值可能是字符串、字符串数组或`undefined`，必须先转换为页面需要的条件；不能用`as string`直接假定外部输入正确。

明确以下职责：

- `TaskSearch`只接收和通知筛选值，不直接调用API。
- 页面协调Router query与加载时机。
- Store管理共享任务与异步状态。
- API模块把条件转换为后端规定的请求参数。
- 后端仍负责数据权限和最终筛选规则。

## 5. 实施顺序

1. 先增加或更新筛选条件类型，并执行类型检查。
2. 修改`TaskSearch.vue`的Props、Emits和选择框。
3. 更新query读取与写入，避免产生无意义空参数。
4. 更新API模块和Pinia Action的参数传递。
5. 补充加载、无结果、失败及清除条件行为。
6. 更新现有测试，而不是仅新增一条成功测试。
7. 更新README或规格说明中的查询条件。

每完成一层就运行相关测试，能比全部改完后再调查更快定位契约断点。

## 6. 必测场景

| 场景 | 预期结果 |
| --- | --- |
| 选择单一担当者 | 只显示该担当者任务 |
| 担当者+状态 | 两个条件同时生效 |
| 担当者+关键字 | 两个条件同时生效 |
| 无匹配任务 | 显示筛选无结果，不显示系统错误 |
| 清除条件 | query移除且恢复全部任务 |
| 刷新带条件URL | 筛选控件和列表状态恢复 |
| 浏览器前进/后退 | 控件与列表跟随URL变化 |
| API失败 | 保留条件并提供重试 |
| 快速切换条件 | 旧响应不覆盖新结果 |

回归测试还应覆盖未使用担当者筛选时原有关键字、状态、详情跳转、新增、修改和删除功能。

## 7. Review与指摘修正

Review请求中写明：

- 规格理解与已确认事项；
- 调查过的文件和数据流；
- 实际改修范围；
- 正常、边界和异常测试结果；
- 未修改部分及理由；
- 仍待确认的限制。

收到指摘后，先判断指摘是否影响类型、URL、API或测试等其他位置，再修改。不要只修Reviewer指出的单行而留下相同问题。
