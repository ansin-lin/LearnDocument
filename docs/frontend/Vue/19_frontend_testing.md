# 第 19 章 前端测试基础与日本项目中的单体测试

功能完成后，前端工程师需要证明它符合设计，并且没有破坏原有功能。本章不使用自动测试工具，而是学习如何从规格提取测试观点、制作単体テスト仕様書、执行浏览器打鍵并保存Evidence。

## 本章目标

- 理解前端测试要确认什么；
- 区分测试阶段与测试执行方式；
- 理解日本项目中的単体テスト、打鍵和Evidence；
- 从设计书提取正常系、異常系和境界値；
- 制作简单的前端単体テスト仕様書；
- 执行测试、记录结果和Bug再现步骤。

## 1. 为什么需要测试

“画面看起来能用”不能证明所有条件都正确。标题为空、达到最大长度、API失败、重复点击、刷新或返回页面时，结果可能完全不同。

测试把以下内容明确记录下来：

```text
什么条件
→ 怎样操作
→ 应该出现什么结果
→ 实际出现什么结果
```

这样修改功能后才能进行Regression Test（回归测试），确认原有功能没有被破坏。

## 2. 什么是前端测试

前端测试不仅检查JavaScript计算，还要确认用户能够观察到的行为：

- 输入、选择、点击和键盘操作；
- Props、Emits和组件显示；
- 表单校验与Message；
- loading、empty、success、error；
- 页面跳转、刷新和直接打开URL；
- API请求与响应后的画面变化；
- 响应式Layout和浏览器实际行为。

## 3. 日本项目常见测试阶段

这些名称的具体范围会因项目而不同，实际工作应以项目的测试计划和定义为准。

| 阶段 | 常见日语 | 基础理解 |
| --- | --- | --- |
| 单体测试 | 単体テスト（UT） | 确认函数、组件、画面或单一功能符合详细设计 |
| 结合测试 | 結合テスト（IT） | 确认页面、API、数据库或外部系统连接正确 |
| 系统测试 | システムテスト（ST） | 从整个系统角度确认业务流程和非功能要求 |
| 验收测试 | 受入テスト（UAT） | 使用方确认系统是否满足业务需求 |

日本现场有时会把“画面単体テスト”定义得比严格意义上的Unit Test更宽，可能包含浏览器操作和API Mock。不要只根据术语猜测范围。

如果测试已经连接真实Backend、真实Database或多个模块，从严格的软件测试分类看，可能已经接近结合测试。但项目现场是否仍称为“画面単体テスト”，应以项目自己的测试计划和定义为准。不能因为由前端开发人员执行，就断定它一定属于UT。

## 4. 测试阶段与执行方式不是同一维度

```text
测试阶段
├─ 単体テスト
├─ 結合テスト
├─ システムテスト
└─ 受入テスト

执行方式
├─ 手動テスト
│   └─ 打鍵
└─ 自動テスト
    ├─ Vitest
    ├─ Vue Test Utils
    └─ Playwright等
```

単体テスト不等于Vitest，也不等于打鍵。同一个测试阶段可以采用手动测试、自动测试或两者组合。

## 5. 什么是打鍵测试

打鍵（だけん）通常指按照测试式样书实际操作浏览器画面，输入、点击、选择、跳转，并确认实际结果是否符合期待结果。它不只是键盘输入，还包括：

- Text输入、Button点击；
- Select、Checkbox、Radio；
- Dialog、上传、搜索；
- 分页、排序、页面跳转；
- Error Message、Loading、Layout；
- Tab键操作、刷新、Back和浏览器实际行为。

即使自动测试通过，真实浏览器中的布局、焦点、文件选择和跨系统连接仍可能需要打鍵确认。

## 6. 前端单体测试应该测试什么

| 对象 | 主要确认内容 |
| --- | --- |
| JavaScript逻辑 | Validation、计算、格式转换、条件判断 |
| Composable | 过滤、搜索、分页状态、业务状态 |
| Pinia Store | action、getter、state变化、API成功与失败 |
| Vue Component | Props、显示隐藏、Button、Emits、Form、Validation |
| 实际页面 | 真实输入、跳转、API联动、Message、Layout、Loading、重复提交 |

测试对象不同，合适的执行方式也不同。纯计算适合自动化，真实Layout和浏览器操作通常更适合打鍵。

## 7. 什么是测试观点

测试观点是“从什么角度确认功能”的分类。它帮助测试人员避免只验证最顺利的一条路径。

### 7.1 正常系

使用有效输入完成正常操作，例如输入合法标题并成功保存。

### 7.2 異常系

确认错误输入、API失败、权限不足等情况下是否正确显示错误，并且不会错误跳转或丢失输入。

### 7.3 境界値

确认限制边界前后。例如最大50字符至少考虑：

```text
49字符：成功
50字符：成功
51字符：错误
```

只测试一个正常值和一个明显错误值，容易遗漏`<`与`<=`写错的问题。

正常系与異常系主要表示业务条件或期待结果类别；境界値是一种测试设计观点，它们不是互斥分类。同一个Case可以同时属于“正常系＋境界値”或“異常系＋境界値”。

| 输入 | 分类 |
| --- | --- |
| 99字符 | 正常系＋境界値 |
| 100字符 | 正常系＋境界値 |
| 101字符 | 異常系＋境界値 |

## 8. 普通前端页面的测试观点清单

### 输入项目

- 必須、最大长度、最小长度；
- 允许的文字种类、空格、特殊字符；
- 初始值、`readonly`、`disabled`。

### Button

- enabled、disabled；
- 单击、连续点击、Enter；
- 请求中的重复提交限制。

### Message

- 正常Message和Error Message；
- 显示位置、内容和消失条件。

### API

- 200、400、401、403、404、409、500；
- timeout和Network Error。

### 页面状态与迁移

- loading、empty、success、error；
- 成功后跳转、失败后不跳转；
- Back、Refresh、直接打开URL。

清单用于帮助思考，不表示每个画面必须机械执行全部项目。应根据规格和风险选择。

## 9. 从设计书制作测试Case

WorkHub的TaskForm规格如下：

```text
项目：Task Title
必須：YES
最大：100文字
保存中：禁止重复提交
```

从规格推导测试：

| No | 观点 | 输入或操作 | 期待结果 |
| --- | --- | --- | --- |
| UT001 | 必須 | 空 | 显示必填错误，不发送请求 |
| UT002 | 正常系 | 普通标题 | 保存成功 |
| UT003 | 境界値 | 99字符 | 保存成功 |
| UT004 | 境界値 | 100字符 | 保存成功 |
| UT005 | 境界値 | 101字符 | 显示长度错误，不发送请求 |
| UT006 | 二重送信 | 保存中连续点击 | 只发送一次请求 |

工作流程是：

```text
设计书
↓
测试观点
↓
测试Case
↓
执行
↓
记录结果
```

## 10. 前端単体テスト仕様書

常见列如下，具体格式以项目模板为准：

| No | 测试观点 | 前提条件 | 操作/输入 | 期待结果 | 结果 | Evidence |
| --- | --- | --- | --- | --- | --- | --- |
| UT001 | 必須 | Task新增画面已打开 | Title为空并点击保存 | 显示“任务标题为必填项”，不发送请求 | ○ | `UT001.png` |
| UT002 | 正常系 | API正常响应 | 输入“规格确认”并保存 | 只发送一次POST，成功后显示完成结果 | ○ | `UT002.png`、Network |

- 前提条件写清账号、数据和页面状态；
- 操作应让其他人能够重复执行；
- 期待结果要可观察，不能只写“正常”；
- 结果常按项目规则记录`○ / ×`、`OK / NG`或实际文字。

## 11. テストデータ与初期状態

每条Case除了操作步骤，还要明确执行前的数据和账号状态：

- 使用哪个账号，该账号拥有什么权限；
- Database中必须预先存在什么数据；
- Case执行后数据会怎样变化；
- 下一条Case是否会受到影响；
- 是否需要恢复、删除或重新建立数据。

例如“删除员工EMP0001”：

```text
前提：EMP0001存在，当前账号具有删除权限
操作：删除EMP0001
期待：删除成功，列表中不存在EMP0001
后处理：重新创建EMP0001
```

测试Case应尽量能够重复执行。不要无意识地让UT002依赖UT001刚刚新增的数据；如果UT001失败，UT002也会无法执行。每条Case应明确自己的前提数据，确实需要顺序执行时则在式样书中明确记录依赖关系。

## 12. 如何执行打鍵

1. 准备规定的浏览器、账号和测试数据；
2. 确认开始页面和前提条件；
3. 严格按Case执行，不临时改变输入；
4. 同时观察页面、Network和Console；
5. 比较期待结果与实际结果；
6. 记录结果并保存规定Evidence；
7. Case之间需要恢复数据时，按项目手顺清理。

执行中发现式样不明确时，应记录确认事项，不能擅自修改期待结果。

## 13. Evidence是什么

Evidence（エビデンス）是用于证明测试执行过程和结果的材料，可能包括：

- 页面截图；
- Network请求与响应；
- Console输出；
- DB查询结果；
- 后端Log；
- 文件输出结果。

Evidence要求属于项目规则，不是每一个前端Case都必然需要截图。截图时应包含能够识别Case和结果的信息，同时遮蔽密码、Token和个人信息。

## 14. Bug发现后的记录

不符合期待结果时，不要只写“有Bug”。至少记录：

| 项目 | 内容 |
| --- | --- |
| 事象 | 实际发生了什么 |
| 前提条件 | 账号、数据、环境和页面 |
| 再現手順 | 可以重复问题的操作步骤 |
| 期待結果 | 规格要求的结果 |
| 実際結果 | 实际页面、响应或日志 |
| 再现率 | 每次、偶发或特定条件 |
| Evidence | 截图、Network、Console或Log |

修正后执行该Case，并对相关旧功能进行Regression Test。

## 15. 完整画面测试案例

以“Task新增画面”为例：

1. 从设计书整理Title、Priority和保存按钮的规格；
2. 设计必填、边界值、API成功、API失败和重复提交Case；
3. 准备正常响应和错误响应条件；
4. 按Case逐条打鍵；
5. 使用Network确认请求次数、Payload和Status；
6. 保存项目要求的Evidence；
7. 记录NG Case的再现步骤；
8. 修正后执行再测试和相关回归。

## 16. 手动Case怎样进入自动测试

UT001的手动步骤是：

```text
浏览器打开TaskForm
→ Title保持为空
→ 点击保存
→ 确认必填Error Message
→ 确认没有发送请求
→ 保存Evidence
```

下一章会把相同Case转换成Vitest与Vue Test Utils代码。自动测试不是另一套测试思想，而是把适合反复执行的Case转换成代码。

## 17. WorkHub练习与检查点

1. 阅读TaskForm规格，整理正常系、異常系和境界値。
2. 至少制作6条単体テストCase。
3. 为每条Case记录账号、权限、前提数据和必要的后处理。
4. 在浏览器执行Case，并使用Network确认API行为。
5. 按项目规则保存Evidence。
6. 人为制造一个错误，记录再現手順、期待結果和実際結果。

- [ ] 能区分测试阶段与测试执行方式。
- [ ] 能解释単体テスト、打鍵、テスト仕様書和Evidence。
- [ ] 能从规格找出正常系、異常系和境界値。
- [ ] 能制作可由他人重复执行的UT式样书。
- [ ] 能准备测试数据，并避免Case无意识地依赖执行顺序。
- [ ] 能使用页面、Network和Console执行确认。
- [ ] 能记录Bug的再现步骤、期待结果和实际结果。
