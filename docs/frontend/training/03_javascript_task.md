# JavaScript 递进练习：有給休暇申請システム

## 1. 任务目标

继续使用已经完成 HTML 和 CSS 的七页面项目，实现账号注册、自动生成社员番号、登录、退出、申请提交、查询、筛选和取消。

本阶段没有后端和数据库。用户资料与申请资料保存在当前浏览器，登录状态只保存在当前标签页会话中。本项目用于学习浏览器 JavaScript，不具备真实系统的身份认证和数据安全能力。

## 2. 安全与运行边界

- 只能使用虚构的培训账号和培训密码，不得输入真实密码或公司账号。
- 不得把密码明文保存在 `localStorage`、`sessionStorage`、URL、DOM 属性或控制台中。
- 使用 Web Crypto 为每个密码生成随机盐和 SHA-256 摘要；该做法只用于避免本练习保存明文，不能替代后端认证和专业密码存储。
- 浏览器使用者能够查看和修改本地数据，因此前端登录不能作为权限控制。
- 页面隐藏、按钮隐藏和前端校验都不能描述为安全措施。
- 使用本地静态服务器打开项目，不依赖 `file://` 下不一致的存储和 Web Crypto 行为。
- 不使用 Vue、React、jQuery、外部 API 和第三方认证库。
- 本练习不实现密码找回；忘记培训密码时只能清除该站点的本地数据并重新注册。

## 4. 浏览器存储设计

| 存储位置 | 键 | 内容 | 生命周期 |
| --- | --- | --- | --- |
| `localStorage` | `paidLeaveUsers` | 注册用户数组 | 清除网站数据前保留 |
| `localStorage` | `paidLeaveApplications` | 全部用户的申请数组 | 清除网站数据前保留 |
| `sessionStorage` | `paidLeaveCurrentUser` | 当前用户的社员番号 | 当前标签页会话 |
| `sessionStorage` | `paidLeaveDraft` | 当前用户未提交的申请草稿 | 当前标签页会话 |
| `sessionStorage` | `paidLeaveLastReceipt` | 最后提交的受付番号 | 当前标签页会话 |

读取 JSON 和写入存储都使用 `try...catch`。读取失败、数据格式错误或写入失败时，必须在页面显示可理解的消息，不能只写入控制台，也不能静默覆盖现有数据。

## 5. 用户数据规格

注册用户对象使用以下结构：

```js
{
  accountId: "yamada.taro",
  passwordSalt: "base64形式のランダム値",
  passwordDigest: "base64形式のダイジェスト",
  name: "山田 太郎",
  department: "development",
```

`accountId` 比较时统一为小写。页面显示所属名称时使用映射对象：

## 6. AUTH-002：注册功能

在 `register.html` 实现以下流程：

1. 读取并去除账号与姓名前后的空格。
2. 账号转换为小写后，检查是否符合 `^[a-z0-9._-]{4,20}$`。
3. 检查账号是否已存在，重复时显示“このアカウントは使用されています”。
4. 检查密码长度为 8～32，并与确认密码一致。
5. 检查姓名和所属已经输入。
6. 自动生成社员番号。
7. 生成随机盐，对“盐＋密码”计算摘要，只保存盐和摘要。
8. 保存成功后显示生成的社员番号，并提供前往登录页的操作。

### 6.1 社员番号自动生成规则

- 格式为 `EMP-NNNNN`，例如第一位用户是 `EMP-00001`。
- 读取已有用户的社员番号，取得最大数字部分后加一。
- 没有用户时从 `EMP-00001` 开始。
- 删除浏览器数据后编号会重新开始，页面需要说明这一点。
- 不使用用户数组长度直接生成编号，避免数据缺号时产生重复编号。

### 6.2 注册成功状态

- 禁止重复点击导致同一账号被保存多次。
- 成功后清空密码和确认密码字段。
- 页面显示姓名、所属和自动生成的社员番号，但不显示密码摘要或随机盐。
- 注册完成不自动登录，使用者需要前往登录页输入账号和密码。

## 7. AUTH-001：登录与退出

### 7.1 登录

在 `login.html`：

1. 根据小写账号查找用户。
2. 使用该用户保存的盐计算输入密码摘要。
3. 使用严格相等比较摘要。
4. 成功时只把 `employeeNumber` 写入 `paidLeaveCurrentUser`，然后前往 `index.html`。
5. 失败时统一显示“アカウントまたはパスワードが正しくありません”，不能泄露账号是否存在。
6. 登录处理中临时禁用按钮，完成后恢复或跳转。

### 7.2 登录状态检查

- 打开五个业务页面时检查 `paidLeaveCurrentUser`。
- 没有登录状态或找不到对应用户时，清除无效会话并跳转 `login.html`。
- 登录页检测到有效会话时，可以显示“ホームへ”入口，但不能造成循环跳转。
- 页面页眉显示当前用户姓名和社员番号。

### 7.3 退出

- 点击“ログアウト”时只清除当前登录状态、申请草稿和最后受付番号。
- 不删除注册用户和已经提交的申请。
- 清除后跳转到 `login.html`。

## 8. 申请数据规格

每条申请增加所属员工字段：

```js
{
  id: "REQ-20260820-001",
  ownerEmployeeNumber: "EMP-00001",
  leaveType: "paid",
  startDate: "2026-08-24",
  endDate: "2026-08-25",
  leaveDays: 2,
  reason: "私用のため",
  handoverStatus: "done",
  note: "緊急連絡はメールで確認します。",
  status: "pending",
  submittedAt: "2026-08-20T11:00:00+09:00"
}
```

所有首页汇总、确认、完成、一览、筛选和取消操作只能使用当前社员番号对应的申请。前端过滤只是练习用数据隔离，不得描述为真实权限控制。

## 9. 休假业务功能

### 9.1 HOME-001

- 从当前用户资料显示姓名、所属和社员番号。
- 计算有給残日数、申請中件数和当月承認済日数。
- 初始有給天数为 12 日，只扣除当前用户 `approved` 的有給和半日休假。
- 没有申请时明确显示 0，不留空。

### 9.2 LEAVE-001

提交前验证：必填、开始日不早于今天、结束日不早于开始日、半日休假只能同一天、申请日数不超过剩余天数、特別休暇必须在連絡事項填写制度名。

错误显示在字段附近，设置 `aria-invalid="true"`，并聚焦第一个错误字段。通过后把带有当前社员番号的草稿保存到 `sessionStorage`，前往 `confirm.html`。从确认页返回时恢复草稿。

申请日数简化为：半日固定 0.5 日，其他按包含首尾日期的自然日计算，本练习不排除周末和日本节假日。

### 9.3 LEAVE-002

- 读取当前用户草稿并使用 `textContent` 显示。
- “修正する”返回输入页且保留草稿。
- “申請する”只能执行一次，处理中禁用按钮。
- 生成 `REQ-YYYYMMDD-NNN`，同一天从 `001` 递增。
- 新申请状态为 `pending`，成功后清除草稿并保存最后受付番号。
- 没有草稿或草稿不属于当前用户时显示错误并提供返回入口。

### 9.4 LEAVE-003

- 显示当前会话最后提交的受付番号。
- 刷新页面不得重复新增申请。
- 没有编号时不显示伪造值，应提示重新申请。

### 9.5 LEAVE-004

- 只显示当前用户的申请。
- 支持状态筛选以及受付番号、申请理由关键字检索。
- 同时应用状态和关键字条件，显示结果件数。
- 无数据时显示“該当する申請はありません”。
- 只有 `pending` 可以取消；取消时更新为 `cancelled`，不能删除记录。
- 取消前显示包含受付番号的确认对话框，保存后立即刷新列表。

## 11. 调试与验收

- 使用 Application 面板检查四个存储键和生命周期。
- 使用断点观察注册对象、摘要计算、登录比较和申请对象生成。
- 使用 Elements 检查错误字段的 `aria-invalid`。
- 控制台没有未处理异常，也没有账号、密码和摘要日志。
- 七个页面共用一个脚本且都能独立初始化。
- 注册、登录、申请、确认、完成、查询、取消和退出形成完整闭环。
- 清除网站数据后能安全回到首次使用状态。

## 12. 日本项目式改修任务

变更规格：

> 同じブラウザーを複数社員が共用するため、ログアウト時に申請入力途中の情報を残さないこと。ただし、登録情報と申請済みデータは削除しないこと。

调查会话存储、退出处理、申请页恢复和确认页读取。修改后验证：退出会清除当前用户、草稿和最后受付番号；重新登录后注册资料与已提交申请仍存在；其他用户不能看到前一用户草稿。
